

##  LLM-based and Retrieval-Augmented   Control Code Generation
基于LLM和检索增强的控制码生成


2023 IEEE 28th International Conference on Emerging Technologies and Factory Automation (ETFA)

### 当前问题和提出的解决方案
标准语言学习模型（例如 GPT-4）可以编写通用代码，但缺乏对专有功能块库（例如，厂商特定的 PID 控制器）的了解。这会导致：
- 效率低下，重复造轮子
	- 在实践中，控制逻辑通常是通过使用“预先指定的功能块来组装，这些功能块封装了常用的算法 。工程师使用这些经过充分测试的专有功能块，可以避免从头编写所有功能 。
	- 由于大多数功能块库是特定供应商专有的，并非公开数据，LLM（如 ChatGPT）并不了解它们
- 难以维护的代码
	- 由于 LLM 无法利用封装好的功能块，生成的代码不仅低效，而且难以理解。
	- 功能块的一个核心价值在于它封装了复杂的逻辑 。如果 LLM 生成的是一长串扁平的逻辑代码，而不是清晰的 `Block_Call()`，那么对于后续维护的工程师来说，理解代码意图的难度将大大增加。
- 在严格的工业环境中容易出现编译错误
	- 案例：GPT-4 错误地使用了变量名 `OUT_MAX` 作为输入，而实际上正确的输出变量名应该是 `OUT` 。这是因为标准输出参数 `OUT` 并没有显式列在 LLM 能够访问的摘要或部分文档中，导致 LLM 只能根据上下文（如功能块绘图）进行错误猜测 。因此必须进行才能通过编译 。


--- 

提出一种检索增强生成 (RAG) 方法，可实时“教导”LLM 了解专有库。
- 索引功能块的 PDF 规范，目的是将非结构化的 PDF 手册转化为计算机可搜索的知识库。
	-  文档加载 (Document Loading): 原文指出，许多功能块库的说明书是 PDF 格式（例如原文使用的 496 页的 OSCAT 库文档）。系统首先使用“Document Loader”（如 `PDFPlumberLoader`）读取这些文件，提取文本和元数据 。
	- 文档分块 (Document Chunking): 为了让信息适应 LLM 的上下文窗口，系统必须将长文档切分。原文强调，最佳实践是创建包含语义相关信息的块 。在原型中，作者编写了一个基于正则表达式（Regular Expression）的自定义分块器，专门识别功能块的章节标题，从而将文档精确切分为一个个独立的“功能块说明”片段（包含输入、输出和功能描述）。
	- 向量嵌入与存储 (Embedding & Storage): 系统使用文本嵌入模型（如 OpenAI 的 `text-embedding-ada-002`）将每个功能块的文本片段转换为浮点数向量 。这些向量随后被存储在向量数据库（如 FAISS）中，以便计算文本之间的相关性 。
- 根据用户提示检索精确的功能块定义。
	- 提示词向量化: 当用户提供控制叙述（Control Narrative）或具体查询（例如“使用 PID 控制器...”）时，系统首先将这段查询文本转换为向量 。
	- 相似度搜索 (Similarity Search):系统的“Vector Store Retriever”会计算查询向量与数据库中存储的功能块向量之间的距离（如使用余弦相似度或欧几里得距离）
	- 提取相关规范: 系统检索出与用户需求最相关的几个功能块说明文档片段 。例如，如果用户请求 PID 控制，系统会检索到库中关于 `FT_PID`、`CONTROL_SET` 等块的详细接口定义（输入/输出参数名称和类型）。
	- 上下文增强: 检索到的这些精确定义被直接“增强（augmented）”附加到发送给 LLM 的原始提示词中，作为上下文参考 。
- 生成有效的 IEC 61131-3 结构化文本
	-  利用提示词模板: 作者设计了一个通用的提示词模板（Prompt Template），明确指示 LLM 使用检索到的“预先指定的功能块”，并遵循特定的输出格式
	- 实例化而非重写: LLM 接收到包含功能块接口定义的上下文后，它生成的 ST 代码会直接实例化（instantiate）这些专有块（例如声明 `PID_Controller: FT_PID;`），而不是尝试从头编写 PID 算法 
	- 参数映射: LLM 能够读取检索到的接口信息，将用户的逻辑需求正确映射到功能块的输入（`VAR_INPUT`）和输出（`VAR_OUTPUT`）引脚上 。
	- 最终产出: 输出结果是一段符合 IEC 61131-3 标准的结构化文本（ST），可以直接导入到 PLC IDE（如 OpenPLC）中进行编译和测试 。

检索增强控制代码生成方法
分为两部分：
	上半部分的一次性执行流程（数据准备）
	和下半部分的循环生成流程（实际代码生成）
#### 一次性执行流程
这部分任务只需要针对每个功能块库（如厂商的 PDF 手册）执行一次，目的是构建一个 LLM 可查询的“外部大脑” 。
- 输入：功能块规格说明 (Function Block Specifications)，这是原始资料，通常是包含数百个功能块定义的 PDF、HTML 或 XML 文档 。
- 步骤 a：文档加载器 (Document Loader) 负责读取源文件。它遍历文件集，提取出其中的文本内容 。
- 步骤 b：文档分块器 (Document Chunker) 。它将加载的长文档切分成较小的片段（Chunks），它会将文档精确地切分为一个个独立的“功能块说明”（包含该块的输入、输出和功能描述）
- 步骤 c：嵌入器 (Embedder) ，它将切分好的文本片段转换为向量（Vectors），即一串浮点数 。这使得计算机可以通过数学计算（距离）来判断两段文本在语义上是否相似 。
- 存储：最终的向量数据被存储在向量库，供后续步骤快速检索 。
#### 循环生成流程
这是用户在日常工作中使用的部分。每当有新的控制需求时，就会运行这个循环 。
- 输入：控制叙述 (Control Narratives) 这是项目的需求文档，通常由工艺工程师用自然语言编写（例如“将T1罐加热到 50 度”） 。
- 步骤 1：控制叙述提取器 (Control Narrative Extractor) 它从冗长的需求文档中提取出具体的、简明的代码生成提示词（Prompt） 产出控制代码生成提示词 (Control code generation prompt)，例如“编写一个使用 PID 控制器的 ST 程序” 。
- 步骤 2：向量库检索器 (Vector Store Retriever) 这是 RAG 的核心连接点。
    - 它首先调用嵌入器，将用户的提示词也转换成向量 。
    - 然后在向量库中进行相似度搜索 (Similarity Search)，寻找与用户需求最匹配的功能块说明 。
    - 结果： 检索到相关的文档片段（即特定功能块的详细定义） 。
- 构建：增强后的提示词 (Augmented control code generation prompt) 系统将用户原始提示词与检索到的功能块上下文 (Function Block Context) 合并。现在的提示词变成了：“请编写一个 PID 程序（用户需求），可以使用以下功能块定义：VAR_INPUT ... END_VAR（检索到的知识）” 。
- 步骤 3：大型语言模型 (Large Language Model) LLM接收这个增强后的提示词。由于提示词里已经包含了它原本不知道的专有库定义，它现在可以根据这些定义生成正确的实例化代码 。产出：控制逻辑代码 (Control logic code)，即符合 IEC 61131-3 标准的结构化文本 。
- 步骤 4：PLC 集成开发环境 (PLC IDE) 最后，生成的代码被导入到 IDE（如 OpenPLC）中。工程师在这里进行编译、仿真测试，并最终下载到物理控制器中 。
### 如何复现
[GitHub - hkoziolek/LLM-CodeGen-RAG: LLM-based and retrieval-augmented Control Code Generation](https://github.com/hkoziolek/LLM-CodeGen-RAG)



图 2 的上半部分。

1. **加载 PDF：** 使用 LangChain 的 `PDFPlumberLoader` 加载 OSCAT 的 PDF 文档 。这将提取文本和元数据。
2. **自定义分块（Critical Step）：** 
    - 作者编写了一个自定义的文档分块器（Custom Document Chunker），基于正则表达式（Regular Expression） 。
    - 策略： 正则表达式需要匹配 OSCAT 文档中每个功能块的小节编号/标题 。
    - 目的： 确保每个切分出来的“块”包含了一个完整的功能块说明（包括输入、输出和功能描述），而不是在句子中间被切断 。这是为了保证 LLM 读到的是完整的说明书。
3. 生成嵌入（Embeddings）： 使用 OpenAI 的 `text-embedding-ada-002` 模型将切分好的文本块转换为向量 。
4. 存储向量： 将向量存储在本地的 FAISS 数据库中 。作者生成的数据库文件大小约为 4.5 MB 。

---
图 2 的下半部分。

1. 设置 LLM： 使用 `gpt-4` 模型（作者使用的是 `gpt-4-32k` version 0613） 。
2. 构建检索器 (Retriever)： 配置 LangChain 的 `RetrievalQA` 链 。
    - 使用基于分数的相似度搜索（Score-based similarity search）或者最大边际相关性（MMR）来查找与用户 Prompt 最相关的文档块 。
    - 配置检索器在返回结果时，包含检索到的源文档（Source Documents），以便在界面上展示参考资料 。
3. 设计提示词模板 (Prompt Engineering)： 可以完全复刻论文 中的 Prompt 模板 。![image.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202512031411046.png)
    - **核心指令：**
        - "Write a self-contained IEC 61131-3 ST function block"（写一个独立的功能块）。
        - "Use the following pre-specified function blocks if useful"（使用以下预定义的功能块）。
        - "Do not write code for the inner body of the function block"（不要写功能块内部的代码，即只做调用）。
        - "Do not include comments... Provide no explanations"（不要注释和解释，只给代码）。

#### 测试与验证

1. **输入测试用例：** 使用论文第 5 节提供的具体 Prompt 进行测试：
    
    - _Test 1:_ "Sample an incoming signal at one-second intervals..."（采样与平均） 。
        
    - _Test 2:_ "Generate a sine wave..."（正弦波与阶梯函数） 。
        
    - _Test 3:_ "Create a PID controller..."（PID 控制器） 。
        
2. **验证生成结果：**
    
    - 查看生成的代码是否正确“实例化”了 OSCAT 库中的块（例如 `SH_1`, `FT_AVG`, `CTRL_PID`） 。
        
    - **注意手动修正：** 论文诚实地指出，GPT-4 生成的代码可能包含小错误（如参数名 `OUT` 写成了 `OUT_MAX`），复现时如果遇到编译错误，需要根据 OSCAT 手册手动微调代码 。
        
3. **OpenPLC 仿真：*
    - 将生成的 ST 代码复制到 OpenPLC Editor 中。
    - 你还需要导入依赖的 OSCAT 源代码（因为 OpenPLC 本身不带 OSCAT，你需要找一个 OpenPLC 版本的 OSCAT 库导入进去） 
    - 编译并运行调试器，观察波形是否符合预期 。
