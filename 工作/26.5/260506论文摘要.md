## 一、总体背景：为什么现在集中研究 C→Rust

C 语言长期用于操作系统、嵌入式系统、驱动程序、基础库和工业遗留系统中。其优势是性能高、对底层硬件控制能力强，但核心问题也非常明显：C 依赖程序员手动管理内存和并发同步，容易产生 use-after-free、double free、缓冲区溢出、悬垂指针、数据竞争等内存安全和线程安全问题。
Rust 的价值在于：它通过所有权、借用检查、生命周期和类型系统，在编译期尽可能排除一大类内存安全和并发安全问题。因此，C→Rust 自动翻译的目标不仅是“把 C 代码翻译成 Rust 代码”，更重要的是：在保持功能正确性的基础上，尽可能生成安全、惯用、可维护的 Rust 代码。
近两年的 SOTA 研究已经不满足于传统 transpiler 的逐句翻译，而是逐渐形成以下趋势：
1. 规则翻译打底：先用已有工具或固定规则，把 C 代码机械地翻译成 Rust 代码。[C2Rust](https://c2rust.com/)也就是说，规则翻译可以快速得到一个运行的 Rust 初始版本，但由于它需要尽量保持 C 的底层行为，往往会生成大量 `unsafe` 代码，因此只能作为后续安全化迁移的基础。
2. 程序分析恢复语义：C 语言里的 `void*` 是一个非常典型的问题。void* data;看不出 `data` 到底是什么类型。因为在c语言中可以进行强制转换，但是 Rust 不喜欢这种模糊表达。Rust 希望类型一开始就尽量清楚。所以 GenC2Rust 这类论文要做的事情就是分析 void* 在程序里到底被怎么使用→ 推断它实际对应什么类型→ 用 Rust 泛型或明确类型来表达
3. LLM 生成更自然的 Rust：也就是语义保持下的代码重写。但是LLM 生成的代码看起来很合理，但不一定真的正确。
4. 编译/测试反馈修复：LLM 生成 Rust  → 编译  → 如果编译失败，读取错误信息  → 让 LLM 或修复模块修改  → 再编译  → 编译通过后运行测试  → 如果测试失败，继续修复
5. unsafe Rust 向 safe Rust 迁移：在保持原程序功能行为的前提下，把裸指针、手动内存管理和强制类型转换等不安全操作，改写为 Rust 的所有权、引用、Option、Result、泛型、slice 等安全抽象。

### 2.1 背景：为什么要把 C 翻译成 Rust
In recent years, there has been a lot of interest in converting C code to Rust, to benefit from the memory and thread safety guarantees of Rust. C2Rust is a rule-based system that can automatically convert C code to functionally identical Rust, but the Rust code that it produces is non-idiomatic, i.e., makes extensive use of unsafe Rust, a subset of the language that doesn’t have memory or thread safety guarantees. At the other end of the spectrum are LLMs, which produce idiomatic Rust code, but these have the potential to make mistakes and are constrained in the length of code they can process.

摘要开头指出，近年来有大量研究关注将 C 代码转换为 Rust，主要原因是 Rust 提供内存安全和线程安全保障。这里的重点不是“Rust 语法更新”，而是系统软件安全问题：大量遗留 C 代码仍然存在内存安全风险，而 Rust 的语言机制可以在编译期消除很多此类问题。
这篇论文首先明确了研究动机：不是为了单纯把一种语言翻译成另一种语言，而是为了让已有 C 项目获得 Rust 的安全收益。C 代码虽然性能强，但内存管理依赖程序员；Rust 则通过所有权和借用检查提供更强的安全保证，因此自动化 C→Rust 迁移具有现实意义。

### 2.2 现有规则工具的问题：C2Rust 能翻译，但生成大量 unsafe Rust
论文摘要中明确提到，C2Rust 是一种规则驱动的系统，可以把 C 自动翻译为功能上相同的 Rust 代码。但是它生成的 Rust 往往并不 idiomatic，并且大量使用 `unsafe`。
也就是说，C2Rust 解决的是“能不能翻译、能不能跑”的问题，但没有很好解决“翻译后是否真正安全、是否符合 Rust 风格”的问题。
### 2.3 现有 LLM 方法的问题：能写出更自然的 Rust，但可靠性不足

摘要随后对比了 LLM 方法。LLM 由于训练数据中包含大量人工编写的 Rust 代码，因此更容易生成惯用、可读性更好的 Rust 代码。但是 LLM 存在两个问题：

1. **可能产生错误**：LLM 生成代码可能无法编译，或者语义与源程序不一致。
2. **上下文长度有限**：真实项目通常包含多个文件和较长函数，无法一次性放入 LLM 上下文窗口。

所以，LLM 解决的是“写得更像 Rust”的问题，但不天然保证“翻译正确”。

汇报时可以这样讲：
### 2.4 方法：用 C2Rust 打底，再用 LLM 分片安全化

C2SaferRust 的核心方法是：

```text
C 项目
→ C2Rust 转换为 non-idiomatic unsafe Rust
→ 将 unsafe Rust 分解成较小 translation units
→ 利用静态分析提取上下文、调用关系和数据流信息
→ 交给 LLM 将局部代码转换为 safer Rust
→ 将翻译结果替换回项目
→ 编译与端到端测试
→ 如果失败，则把错误反馈给 LLM 继续修复
```

论文摘要中最关键的句子是：C2SaferRust combines the strengths of C2Rust and LLMs。也就是说，它不是完全依赖规则，也不是完全依赖 LLM，而是采用混合路线。

### 2.5 实验果：减少 unsafe 代码，同时保持测试通过

论文在 7 个真实程序组成的 benchmark 上进行实验。这些程序来自 GNU Coreutils，并配套端到端测试用例。摘要中给出的主要结果是：

- 原始指针数量最多减少 38%；
- unsafe 代码量最多减少 28%；
- 翻译后的程序仍然通过所有测试；
- 相比两类先前的 safer Rust 转换方法，C2SaferRust 具有更好的综合表现。

==论文并不是声称完全生成 safe Rust，而是强调“safer Rust”。也就是说，方法能够减少 unsafe 成分，但并没有完全消除 unsafe。

## 3. 论文流程图与讲解
  
![c2saferust_fig1.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/20260506225230779.png)

### 3.1 图中各模块含义


#### （1）Transpiler：先得到 non-idiomatic Rust

左下角表示输入是 C project source code，首先经过 C2Rust transpiler，得到 non-idiomatic Rust。这个阶段并不追求代码安全和优雅，而是先保证整体项目能翻译成 Rust 形式。
#### （2）Orchestrator Agent：代码分解和翻译顺序安排
左上角的 Orchestrator Agent 做两件事：
1. 将代码分解为 translation units；
2. 按照依赖关系确定翻译顺序。
真实项目不能随机选择代码片段翻译。必须考虑调用图和依赖关系。
#### （3）Static Analysis Agent：提取上下文信息

中间的 Static Analysis Agent 包括：

- Callgraph Analysis：分析函数调用关系；
- Dataflow Analysis：分析变量活跃性、输入输出依赖；
- Program Slicing：提取当前 translation unit 相关上下文。

这一部分体现了 C2SaferRust 的 neuro-symbolic 特征：

LLM 负责生成；
静态分析负责约束和补充语义上下文。
#### （4）Translation Agent：LLM 局部翻译

右上角 Translation Agent 做三步：

Retrieve context检索上下文
Compose translation prompt构造翻译提示词
LLM 生成 safer Rust

这说明 LLM 并不是只看到孤立代码，而是结合静态分析得到的上下文进行重写。

#### （5）Validation / Repair Agent：编译、测试与反馈修复

右侧的 Validation Agent 会把 LLM 生成的翻译替换回项目，然后编译和运行测试。如果失败，就进入 Repair Agent，将错误信息组织成 repair prompt，再交给 LLM 修复。

这部分是方法可靠性的关键：

LLM 不可信 → 需要编译器和测试用例作为外部约束；
一次生成不成功 → 用错误反馈进行迭代修复。
