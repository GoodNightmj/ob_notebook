# 一、C2SaferRust

## 1. 解决 C2Rust 中什么问题

C2SaferRust 主要解决的是 **C2Rust 规则翻译后生成大量 non-idiomatic unsafe Rust 的问题**。

C2Rust 作为规则翻译器，可以把 C 代码自动翻译成 Rust，并尽量保持原程序的功能等价。但是它的目标主要是“翻译成功”和“行为保持”，不是生成安全、惯用、可维护的 Rust。因此，C2Rust 翻译结果通常会保留大量 C 风格低层操作，例如裸指针、手动内存访问、`unsafe` 代码块等。C2SaferRust 论文明确指出，C2Rust 能自动生成功能等价 Rust，但结果是 non-idiomatic Rust，并且大量使用 unsafe Rust，而 unsafe Rust 并不具备 Rust 原本的内存安全和线程安全保证。([arXiv](https://arxiv.org/abs/2501.14257?utm_source=chatgpt.com "C2SaferRust: Transforming C Projects into Safer Rust with NeuroSymbolic Techniques"))

简单说，C2Rust 的问题是：

```text
能翻译，但翻译出来的 Rust 不够安全、不够 Rust 风格。
```

例如，C2Rust 可能把 C 中的指针数组访问：

```c
int sum(int *arr, int len) {
    int s = 0;
    for (int i = 0; i < len; i++) {
        s += arr[i];
    }
    return s;
}
```

翻译成类似下面的 Rust：

```rust
unsafe fn sum(arr: *const i32, len: i32) -> i32 {
    let mut s = 0;
    let mut i = 0;
    while i < len {
        s += *arr.offset(i as isize);
        i += 1;
    }
    s
}
```

这个版本虽然是 Rust，但仍然是 C 风格的 Rust：使用裸指针、指针偏移和 `unsafe`。它没有真正转换成 Rust 中更安全的 `slice`、`iterator`、`Option` 等表达。

所以 C2SaferRust 关注的问题可以概括为：

> **如何在 C2Rust 已经生成可运行 Rust 初稿的基础上，进一步减少 unsafe 和 raw pointer，使其更接近 safer Rust。**

---

## 2. 解决方法

C2SaferRust 不是完全抛弃 C2Rust，而是采用 **C2Rust + 静态分析 + LLM + 测试验证** 的混合路线。

它的整体流程是：

```text
C 项目
→ C2Rust 规则翻译
→ non-idiomatic unsafe Rust
→ 静态分析与代码切片
→ LLM 局部重写
→ 编译和测试验证
→ safer Rust
```

论文的核心思路是：先用 C2Rust 得到一个功能上可对应原 C 程序的 Rust 初始版本；然后把这个 unsafe Rust 项目分解成多个较小的代码切片，每个切片单独交给 LLM 改写为 safer Rust；每处理完一个切片，就运行端到端测试，确认程序行为仍然保持正确。论文还报告，在其基准上最多减少 38% raw pointers 和 28% unsafe code，同时仍然通过所有测试用例。([arXiv](https://arxiv.org/abs/2501.14257?utm_source=chatgpt.com "C2SaferRust: Transforming C Projects into Safer Rust with NeuroSymbolic Techniques"))

具体来说，它分成几步：

### 第一步：C2Rust 打底

先用 C2Rust 把 C 项目翻译成 Rust 初始版本。这个版本虽然 unsafe 很多，但它保留了原 C 项目的基本结构和行为。

这一步解决的是：

```text
先把 C 项目变成一个 Rust 项目。
```

### 第二步：静态分析

系统对 C2Rust 生成的 Rust 代码进行静态分析，包括调用关系、数据流关系、程序切片等。

这一步解决的是：

```text
哪些代码片段互相关联？
哪些 unsafe 操作可以局部改写？
当前代码片段需要哪些上下文？
```

### 第三步：代码切片

因为整个项目太大，不能一次性全部丢给 LLM，所以 C2SaferRust 把 unsafe Rust 拆成多个小切片。

每个切片可以理解为一个局部翻译单元，例如某个函数、某个 unsafe block 或某段相关代码。

### 第四步：LLM 局部重写

LLM 的任务不是从零翻译 C，而是把 C2Rust 已经生成的 unsafe Rust 片段改写成更安全的 Rust。

例如：

```rust
unsafe fn sum(arr: *const i32, len: usize) -> i32 {
    let mut s = 0;
    for i in 0..len {
        s += *arr.add(i);
    }
    s
}
```

可以重写成：

```rust
fn sum(arr: &[i32]) -> i32 {
    arr.iter().sum()
}
```

这一步的目标是减少：

```text
raw pointer
unsafe block
C 风格循环
手动内存操作
```

并尽量使用：

```text
slice
reference
Option
Result
iterator
Vec
Box
```

### 第五步：编译和测试验证

每次 LLM 改写后，都要把代码替换回项目中，然后运行测试，确认行为没有被破坏。

因此，C2SaferRust 的核心优势不是单纯使用 LLM，而是：

```text
C2Rust 提供稳定初稿；
静态分析控制上下文；
LLM 做局部安全化改写；
测试用例检查行为是否保持。
```

---

## 3. 仍然存在什么问题没有解决

C2SaferRust 仍然有几个明显限制。

### 第一，它只是减少 unsafe，不是完全消除 unsafe

论文结果是最多减少 38% raw pointers 和 28% unsafe code，这说明它提高了安全性，但并没有把所有 unsafe 都消除掉。也就是说，它得到的是 **safer Rust**，不是严格意义上完全 safe Rust。([arXiv](https://arxiv.org/abs/2501.14257?utm_source=chatgpt.com "C2SaferRust: Transforming C Projects into Safer Rust with NeuroSymbolic Techniques"))

可以这样讲：

```text
C2SaferRust 解决了 unsafe 过多的问题，但没有彻底解决 unsafe 消除问题。
```

### 第二，它依赖测试覆盖率

C2SaferRust 用端到端测试验证行为保持。如果测试用例没有覆盖某些边界情况，那么即使测试通过，也不能证明翻译后的 Rust 在所有输入下都等价。

例如，数组越界、空指针、异常输入、并发交错等情况，如果测试没有覆盖，仍然可能隐藏错误。

所以它的问题是：

```text
测试通过只能说明已测输入下行为正确，不能证明语义完全等价。
```

### 第三，LLM 局部重写可能破坏全局一致性

C2SaferRust 通过切片降低 LLM 上下文压力，但切片也会带来问题：当前切片改对了，不代表和其他模块的接口、调用关系、生命周期关系都完全一致。

例如，LLM 把某个函数参数从裸指针改成 `&mut T`，但调用方没有同步修改，就可能导致项目级编译或行为问题。

### 第四，仓库级复杂问题仍然没有完全解决

C2SaferRust 已经面向真实项目，但它仍然主要围绕 unsafe 片段安全化。对于宏、复杂构建系统、跨语言库、第三方依赖、复杂模块重构等更系统的仓库级问题，它并没有完全解决。

---

# 二、GenC2Rust

## 1. 解决 C2Rust 中什么问题

GenC2Rust 主要解决的是 **C2Rust 或已有 C→Rust 翻译工具难以把 C 中的 `void*` 多态用法翻译成 Rust 泛型的问题**。

C 语言没有真正的泛型，所以很多 C 程序会用 `void*` 来模拟泛型。例如，一个通用链表、哈希表、排序函数、容器库，可能都会把数据写成 `void*`：

```c
void push(void *data);
void *pop();
```

在 C 里，`void*` 的意思是：

```text
这是一个未知类型的指针，具体是什么类型由程序员自己强制转换。
```

但是 Rust 不鼓励这种弱类型写法。Rust 有自己的泛型机制，应该写成：

```rust
fn push<T>(data: T) { ... }
fn pop<T>() -> T { ... }
```

已有翻译工具往往不能自动把 C 中这种 `void*` 的多态使用方式映射成 Rust 的泛型指针或泛型类型。GenC2Rust 摘要中明确指出，现有工具经常无法把 C 中 `void*` 的多态用法映射到 Rust 中更惯用的 generic pointers，这会导致翻译结果仍然是 non-idiomatic Rust，并需要大量人工重构。([Researchr](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/54/GenC2Rust-Towards-Generating-Generic-Rust-Code-from-C "GenC2Rust: Towards Generating Generic Rust Code from C (ICSE 2025 - Research Track) - ICSE 2025"))

所以 GenC2Rust 关注的问题是：

```text
C 中用 void* 模拟泛型；
C2Rust 翻译后仍然保留 void* / raw pointer 风格；
没有转成 Rust 中真正的泛型抽象。
```

也就是说，它解决的不是所有 C2Rust 的 unsafe 问题，而是其中一个非常典型、非常困难的类型迁移问题：

> **如何把 C 中弱类型的 `void*` 用法，恢复成 Rust 中强类型的泛型表达。**

---

## 2. 解决方法

GenC2Rust 的方法是 **静态分析 + 类型约束推导 + `void*` 重类型化为 Rust 泛型**。

它的整体流程可以概括为：

```text
C 程序中的 void*
→ 静态分析 void* 的使用位置
→ 构建 typing constraints
→ 推断 void* 的真实类型关系
→ 将 void* 重写为 Rust generic pointers
→ 生成 generic Rust code
```

论文摘要明确说，GenC2Rust 会静态分析 C 程序中 void pointers 的使用，计算 typing constraints，然后把 void pointers 重新类型化为 generic pointers；论文还在 42 个不同规模、不同领域的 C 程序上评估其可扩展性和正确性。([Researchr](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/54/GenC2Rust-Towards-Generating-Generic-Rust-Code-from-C "GenC2Rust: Towards Generating Generic Rust Code from C (ICSE 2025 - Research Track) - ICSE 2025"))

具体理解如下。

### 第一步：找出所有 `void*`

比如 C 代码中有：

```c
void *data;
void set(void *x);
void *get();
```

系统先识别这些 `void*` 出现的位置。

### 第二步：分析 `void*` 怎么被使用

比如：

```c
int *p = (int*)data;
*p = 10;
```

这说明 `data` 在这里实际上被当成 `int*` 使用。

又比如：

```c
struct Node *n = (struct Node*)data;
n->value = 1;
```

这说明 `data` 实际指向 `struct Node`。

### 第三步：构建类型约束

系统会从这些使用方式中抽取约束。

例如：

```text
data 在位置 A 被转换成 int*
data 在位置 B 被传入函数 f
函数 f 期望参数类型为 T*
因此 data 的类型需要和 T 兼容
```

这些关系组合起来，就是 typing constraints。

### 第四步：推导真实类型关系

如果分析发现某个容器函数实际上可以处理不同类型的数据，那么它可能不应该被翻译成某一个具体类型，而应该翻译成 Rust 泛型。

例如 C 中：

```c
void list_push(List *list, void *data);
void *list_get(List *list, int index);
```

可以迁移成 Rust 泛型风格：

```rust
struct List<T> {
    data: Vec<T>,
}

impl<T> List<T> {
    fn push(&mut self, data: T) { ... }
    fn get(&self, index: usize) -> Option<&T> { ... }
}
```

这样就把 C 中不安全的 `void*` 多态，迁移成 Rust 中类型安全的泛型。

### 第五步：生成 generic Rust code

最终目标是让 Rust 代码不再依赖 `*mut c_void` 或大量强制类型转换，而是使用泛型表达真实类型关系。

所以 GenC2Rust 的核心贡献可以概括为：

```text
把 C 中隐式、弱类型、靠程序员约定维护的多态关系，
转换成 Rust 中显式、强类型、由编译器检查的泛型关系。
```

---

## 3. 仍然存在什么问题没有解决

GenC2Rust 的局限也很明显。

### 第一，它主要解决 `void*`，不是解决全部 C→Rust 安全迁移问题

GenC2Rust 聚焦的是 `void*` 到 Rust 泛型的迁移。它不直接解决 C2Rust 中所有 unsafe block、裸指针、生命周期、所有权、宏、并发、构建系统等问题。其摘要也明确把工作范围放在 `void pointers` 的静态分析、类型约束计算和 generic pointers 重类型化上。([Researchr](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/54/GenC2Rust-Towards-Generating-Generic-Rust-Code-from-C "GenC2Rust: Towards Generating Generic Rust Code from C (ICSE 2025 - Research Track) - ICSE 2025"))

所以它的问题是：

```text
解决点很关键，但范围比较窄。
```

### 第二，它不能保证所有 `void*` 都能成功泛型化

有些 `void*` 用法非常复杂，例如：

```text
同一个 void* 在不同路径下被转换成不同类型；
void* 被写入全局变量；
void* 经过函数指针传递；
void* 和宏、内存池、手动偏移混合使用；
void* 指向的数据生命周期不清楚。
```

这种情况下，类型约束可能不完整、不一致，或者无法推导出合适的 Rust 泛型表示。

### 第三，它不直接解决所有权和生命周期问题

即使成功把 `void*` 推导成泛型 `T`，Rust 还需要知道：

```text
谁拥有 T？
T 是借用还是所有权转移？
能不能可变借用？
生命周期应该多长？
是否需要 Box<T>、Rc<T>、Arc<T>？
```

这些问题不是单纯类型泛型化就能完全解决的。

### 第四，它更偏程序分析，不解决 LLM 翻译不稳定问题

GenC2Rust 主要是静态分析和类型迁移方法，不是一个完整的 LLM 反馈修复框架。因此，它没有解决 LLM 一次性翻译不稳定、测试反馈修复、多轮搜索等问题。

---

# 三、LAC2R

## 1. 解决 C2Rust 中什么问题

LAC2R 解决的是两个层面的问题。

第一个层面是 **C2Rust 等规则翻译方法生成的 Rust 虽然功能等价，但往往 non-idiomatic、unsafe、可维护性差**。LAC2R 论文中指出，传统规则方法如 C2Rust 目标是保持功能等价，但通常生成包含 unsafe blocks 和 low-level constructs 的 non-idiomatic Rust，从而削弱安全性和可维护性。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

第二个层面是 **现有 LLM 方法虽然能生成更 idiomatic、更安全的 Rust，但一次性翻译和单路径迭代修复不稳定**。论文指出，LLM 方法缺少等价性保证，存在 hallucination 问题；现有方法通常把 LLM 限制在静态 prompt-response 或单条 refinement 轨迹中，没有系统探索多条可能的修复路径。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

所以 LAC2R 不是只解决 C2Rust 的问题，而是进一步解决：

```text
C2Rust 规则翻译：稳定但 unsafe、不惯用；
LLM 直接翻译：自然但不稳定、缺少等价保证；
已有 LLM 修复：通常只沿单一路径迭代，容易陷入错误修复方向。
```

一句话概括：

> **LAC2R 要解决的是：如何把 C→Rust 翻译从“一次性生成”或“单路径修复”，变成一个可搜索、可反馈、可规划的多轨迹安全化翻译过程。**

---

## 2. 解决方法

LAC2R 的方法是 **LLM Agent + VFT + MCTS 多轨迹搜索修复**。

它的整体流程可以概括为：

```text
C 代码
→ C2Rust / 初始 Rust 版本
→ LLM 生成或修复候选
→ VFT 发现语义差异
→ 编译/测试反馈
→ MCTS 组织多条修复轨迹
→ 选择更优的 safe Rust 翻译结果
```

论文提出两个关键机制：

1. **Virtual Fuzzing-based equivalence Test，VFT**
    
2. **Monte Carlo Tree Search，MCTS**
    

论文摘要中说明，VFT 用来引导 LLM 找到会导致 C 函数和 Rust 对应函数行为分歧的输入，并生成诊断信息；LAC2R 使用 MCTS 系统组织 LLM 诱导出的中间步骤，以形成正确的翻译轨迹。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

---

## 2.1 VFT：虚拟模糊等价测试

VFT 的作用是帮助 LLM 找到：

```text
哪些输入会让原 C 程序和翻译后的 Rust 程序表现不一致？
为什么会不一致？
应该怎么修？
```

普通测试是实际运行程序，输入测试数据，看输出是否一致。

VFT 更像是让 LLM 模拟分析：

```text
给定 C 代码和 Rust 代码；
让 LLM 推理哪些输入可能造成行为差异；
再让 LLM 解释差异产生的原因；
然后把这个诊断反馈给修复过程。
```

例如，C 函数是：

```c
int get(int *arr, int len, int i) {
    if (i < len) return arr[i];
    return -1;
}
```

Rust 翻译版本如果漏掉了 `i < len` 的边界条件，VFT 可能会推理出：

```text
当 i >= len 时，C 返回 -1；
Rust 版本可能 panic 或返回错误结果；
因此边界条件处理不一致。
```

这个信息就可以作为 repair feedback。

论文中也说明，VFT 通过提示 LLM 识别会诱发原 C 函数与 Rust 对应函数行为分歧的输入参数，并生成诊断信息，来指导 Rust 代码 refinement。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

---

## 2.2 MCTS：多轨迹搜索修复

MCTS 是 Monte Carlo Tree Search，中文一般叫 **蒙特卡洛树搜索**。

这里可以简单理解为：

> 不只尝试一条修复路径，而是同时探索多条可能的修复路径，并根据编译、测试、安全性等反馈选择更有希望的路径继续深入。

以前很多 LLM 翻译流程是：

```text
生成版本 1
→ 报错
→ 修复成版本 2
→ 再报错
→ 修复成版本 3
```

这是一条单路径。

问题是，如果第一步修错方向，后面可能越修越偏。

LAC2R 改成：

```text
初始 Rust
├── 修复路径 A
│   ├── A1
│   └── A2
├── 修复路径 B
│   ├── B1
│   └── B2
└── 修复路径 C
    ├── C1
    └── C2
```

然后系统根据奖励值判断哪条路径更好。

奖励可以来自：

```text
能否编译通过；
能否通过测试；
unsafe 是否减少；
linter warning 是否减少；
功能等价性是否更好；
VFT 是否发现更少行为差异。
```

论文中明确说，LAC2R 使用 MCTS 系统探索多条 refinement trajectories，并组织 LLM 产生的中间步骤来获得正确翻译。([arXiv](https://arxiv.org/abs/2505.15858 "[2505.15858] Search-Based Multi-Trajectory Refinement for Safe C-to-Rust Translation with Large Language Models"))

---

## 2.3 多 LLM 和 Agent 化

LAC2R 还强调 LLM 的 agentic capability，也就是不再把 LLM 只当作一次性问答工具，而是让它参与多步骤推理、诊断和修复。

论文指出，现有方法大多把 LLM 限制在静态 prompt-response 行为中，而 LAC2R 关注如何利用 LLM 的 agentic problem-solving capability。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

因此，LAC2R 的方法可以总结为：

```text
LLM 不是只负责“翻译一次”，而是参与：
生成候选
发现差异
解释错误
修复代码
在搜索树中形成多条 refinement 轨迹
```

## 3. 仍然存在什么问题没有解决

LAC2R 比前两篇更前沿，但也不是万能的。

### 第一，计算成本更高

因为它要探索多条修复轨迹，还要多次调用 LLM、执行 VFT、运行编译和测试，所以成本一定高于普通一次性翻译或简单迭代修复。

可以这样理解：

```text
C2SaferRust：一个切片一条修复路线为主；
LAC2R：多个候选、多条轨迹、多轮搜索。
```

这提升了成功率，但也提高了时间和算力成本。

### 第二，VFT 依赖 LLM 的推理能力，不是真正运行程序

论文中提到，VFT 的一个特点是 compile-free，但它基于 LLM 作为“代码执行器”的假设。也就是说，它不是真正跑程序，而是让 LLM 推理可能导致行为分歧的输入和原因。([arXiv](https://arxiv.org/html/2505.15858v2 "Large Language Model-Powered Agent for C to Rust Code Translation"))

这带来的问题是：

```text
LLM 可能推理错；
可能漏掉真实反例；
可能生成看似合理但不准确的诊断；
复杂指针和并发行为很难纯靠推理覆盖。
```

### 第三，它仍然不能形式化证明语义等价

LAC2R 通过测试、VFT 和 MCTS 提高正确性，但它仍然不是严格的形式化验证方法。

也就是说，即使最终代码通过测试，也不能证明：

```text
对所有输入都和 C 程序等价；
所有安全问题都被消除；
所有边界情况都被覆盖。
```

### 第四，复杂仓库级工程问题仍然困难

LAC2R 主要解决的是 C-to-safe-Rust 翻译中的多轮 refinement 和搜索问题。对于完整仓库里的宏系统、构建脚本、FFI、平台相关代码、第三方库依赖、复杂全局状态等问题，它仍然不能完全解决。

### 第五，safe Rust 的生成仍受测试和评价指标约束

如果评价指标只关注编译通过、测试通过、unsafe 减少，那么模型可能生成“测试上正确”的代码，但不一定是工程上最优、性能最好、接口设计最合理的 Rust。

# 四、三篇论文的整体对比

可以用这个表直接放 PPT：

|论文|解决 C2Rust / 现有方法中的什么问题|解决方法|仍未解决的问题|
|---|---|---|---|
|**C2SaferRust**|C2Rust 生成大量 non-idiomatic unsafe Rust，raw pointer 和 unsafe block 多，安全收益有限|C2Rust 打底；静态分析和代码切片；LLM 局部重写；端到端测试验证|只能减少 unsafe，不能完全消除；依赖测试覆盖；切片可能影响全局一致性；复杂仓库级问题仍困难|
|**GenC2Rust**|C2Rust / 现有工具难以把 C 中 `void*` 多态用法翻译成 Rust 泛型，导致弱类型和非惯用 Rust|静态分析 `void*` 使用方式；构建类型约束；推导真实类型关系；重类型化为 Rust 泛型|主要解决 `void*`，范围较窄；不能解决所有权、生命周期、宏、并发等问题；复杂 `void*` 用法仍可能难处理|
|**LAC2R**|C2Rust 稳定但 unsafe；LLM 自然但不稳定；已有 LLM 方法多是单路径修复，缺少系统搜索|LLM Agent；VFT 发现行为差异；MCTS 组织多条 refinement 轨迹；编译/测试反馈修复|计算成本高；VFT 依赖 LLM 推理，不是真实执行；不能形式化证明等价；复杂仓库级工程问题仍未完全解决|

# 五、你汇报时可以用的总结话术

可以这样讲：

> 这三篇论文其实代表了 C→Rust 翻译的三个递进方向。C2SaferRust 主要解决 C2Rust 生成大量 unsafe Rust 的问题，它通过“C2Rust 打底 + 静态分析切片 + LLM 局部重写 + 测试验证”来减少 unsafe。GenC2Rust 则进一步聚焦 C 语言中 `void*` 这种弱类型多态机制，尝试通过静态分析恢复类型约束，并把它迁移为 Rust 的泛型表达。LAC2R 则关注 LLM 翻译和修复过程本身的不稳定性，把 C→Rust 翻译建模为多轨迹搜索问题，利用 VFT 发现行为差异，并通过 MCTS 组织多条修复路径。整体来看，当前 SOTA 的趋势已经从简单规则翻译，逐步转向“规则翻译打底、程序分析恢复语义、LLM 安全化重写、编译测试反馈修复”的综合路线。
