## 多阶段翻译与中间表示

首先，介绍编译器中间端与后端的大致结构。需要指出的是，编译器前端的输出通常为抽象语法树。该输出结果将作为后续处理的输入，体现出编译器各阶段之间“流水线式”的结构安排。

![4.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291059836.png)


在生成抽象语法树之后，将进入初步的翻译阶段。在后续讲解代码生成算法时，将详细说明所谓“翻译的变”。在该阶段，抽象语法树被转换为另一种形式，以便进行后续处理。该初步翻译过程称为“翻译1”，其输入为抽象语法树，输出为编译器的第一个中间表示。故可将“翻译1”视为一个具有清晰输入与输出接口的模块，功能明确，结构清晰。

接着，该中间表示将作为下一阶段的输入，进入“翻译2”阶段。该阶段以中间表示1为输入，生成新的中间表示2作为输出。以此类推，整个编译过程形成一个多阶段、多层次的翻译与中间表示体系。

如图所示，编译过程可包含多个翻译阶段与相应的中间表示。该结构的设计更接近一门“工程艺术”而非绝对科学。换言之，编译器中应设置多少个中间翻译阶段，采用何种中间表示形式，以及各阶段之间如何转换，均由编译器设计者根据实际需求自由决定。在实际设计中，并不存在唯一的标准答案。设计决策需综合考虑多个因素，如编译器的设计目标、源语言特性、目标代码生成要求等。因此，编译器的中间结构与翻译策略需灵活掌握并加以调整。

最终，在经过多阶段的翻译后，编译器将生成汇编代码，或是接近汇编形式的伪代码。该输出将作为后端处理的输入。关于后端的具体结构与处理机制，将在后续内容中进一步讨论。

从整体架构来看，编译器中间端的结构相对清晰：由一系列中间表示组成，并通过逐层的翻译过程不断转换。例如，从一个中间表示出发，经过一次翻译得到下一个中间表示，随后继续向下翻译，依次类推。

编译器采用多层中间表示结构具有深刻的合理性。从本质上看，编译器的任务是将一种高级语言（如 C 或 Java）翻译为一种底层语言（如 x86 汇编）。由于二者在语义与抽象层次上差异巨大，若试图一次性完成翻译，难度极大，且效率低下。因而，采用多个中间表示，通过分阶段的逐步翻译，有助于简化编译过程，提高系统的可维护性与优化灵活性。

从抽象层次角度观察，C语言显然处于比汇编语言更高的层级。因此，编译器的核心任务之一即是**逐步降低抽象层次**，最终生成可执行的汇编代码。若试图在一个步骤中直接完成从高级语言到低级语言的转换，将面临极高的复杂性与实现难度。故现代编译器通常采用分阶段设计，将整个翻译过程拆解为多个层次递进的步骤。具体而言，编译器首先将高级语言翻译为一种较为简单的中间表示，作为第一次抽象层次的降低。随后，通过多个连续的翻译阶段，每一步进一步简化结构与语义，最终生成汇编代码。

如前所述，编译器的阶段划分方式与其所处理的编程语言以及整体设计理念密切相关。例如，在 GCC 编译器中，内部使用了三个主要的中间表示，因此相应地包含三个主要的翻译阶段。而在其他编译器中，中间表示的数量可多可少，这取决于具体实现需求，并无统一标准。后续内容将结合两个具体实例展开分析，以加深对多阶段结构的理解。同时，也将观察最简单的编译器结构如何对该流程进行简化与实现。
## 代码生成阶段的基本任务

在最简单的编译器结构中，整个编译流程可能仅包含一个翻译阶段。即：以抽象语法树为输入，经过一次翻译过程，直接生成汇编代码。该过程通常被称为**代码生成（Code Generation）**。该术语之所以得名，是因为该阶段的输出结果即为目标机器可识别、可执行的汇编语言格式。

![5.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291100696.png)

在早期的编译器设计中（如20世纪六七十年代），这种架构曾被广泛采用。彼时，许多编译器在抽象语法树阶段，甚至语法分析阶段，便直接生成汇编代码。然而，随着编译技术的发展，该类“一遍生成代码”的设计在现代编译器中已不常见。这是由于直接从高层抽象语法树生成汇编代码，其所涉及的抽象层次跨度过大，导致模块实现与维护难度显著上升。因此，现代编译器普遍采用**多阶段翻译与多种中间表示**的设计理念，逐步降低抽象层次，从而提升编译过程的灵活性与可维护性。

明确了代码生成的整体架构后，可以进一步具体分析代码生成模块，即该编译阶段所承担的任务。从宏观角度出发，首先对代码生成阶段需要完成的主要工作进行概述，随后结合具体实例，深入剖析代码生成过程中的各个环节及其实现方法。

代码生成的最主要任务是将源程序翻译成目标机器代码。这里所称的“目标机器”并不一定指真实的硬件平台，既可以是真实的物理机器，如 x86、ARM、MIPS 等架构，也可以是虚拟机环境，例如 Java 虚拟机（JVM）、Android 平台中的 Dalvik 虚拟机或其他语言所采用的虚拟机。

所谓生成目标代码，通常指将源代码转换为抽象层次较低的代码，但这并不意味着目标代码必须针对真实的物理机器。实际上，目标代码的范围更为广泛，既可以是物理机器的指令集，也可以是某种虚拟机的代码。在这一过程中，核心目标是保证等价性。所谓等价性，即源代码所表达的功能和行为，目标代码必须保持完全一致。例如，若源代码执行输出数字 5，则生成的目标代码也必须准确输出数字 5。然而，如何保证这种等价性是一项极具挑战性的任务。事实上，许多现代编译器，如 GCC 和 LLVM，均存在某些翻译错误或漏洞，导致部分源程序被错误编译，这也是编译器领域内的重要研究课题之一。

具体而言，代码生成阶段主要包含两个关键子任务。其一，是将源程序中的数据合理分配到机器上的计算资源。换言之，源程序中使用的各种数据必须映射到机器的合适位置。其二，对于负责任且高质量的编译器来说，还需考虑生成代码的效率。由于实现同一高层操作可能对应多种不同的指令序列，编译器应选择效率最高、性能最佳的指令组合完成该操作。因此，在设计和实现代码生成模块时，开发者需要始终牢记两个核心概念：功能等价性与代码效率，这直接影响生成代码的正确性与运行性能。
## 数据到计算资源的映射策略

首先讨论如何将源程序中的数据分配到机器的计算资源上。以 C 语言为例，源程序中的数据主要包括全局变量、函数的局部变量或局部作用域内的变量、动态分配的内存空间（如通过 `malloc`、`free` 等操作管理的内存）。代码生成模块需要合理分配相应的机器资源，确保程序的正确执行和高效运行。

计算资源具体包括以下几类：

- **寄存器**：处理器内部高速存储单元，数量有限，通常为 8 个、16 个或 32 个不等。

- **数据区**：用于存放全局变量及静态数据。

- **代码区**：存放编译生成的程序指令，包括汇编代码或二进制代码。

- **栈区**：用于函数调用时保存返回地址、参数以及局部变量，实现函数调用和返回机制。

- **堆区**：用于动态内存分配，存放运行时通过如 `malloc` 等方式申请的内存空间。

编译器的重要任务是根据源程序特点及设计目标，合理为源程序中的数据分配机器计算资源。例如，全局变量应存放在数据区，动态分配的变量则放置于堆区。若分配不当，程序运行结果可能出错。比如，若将动态分配的数据错误地放置在栈区，由于函数调用返回时栈空间释放，数据将随之消失，无法满足预期的数据生命周期要求。因此，代码生成阶段必须结合程序语义特征与编译器设计目标，合理规划计算资源的分配，确保程序正确性和稳定性。

某些问题较为微妙，例如局部变量应存放于内存还是寄存器，往往需要权衡。结构体变量通常放在函数的局部存储区，即栈帧内。一般情况下，局部变量被分配到栈帧中。但如果编译器实现简单或设计宽松，局部变量也可存放在堆区，譬如为某局部变量动态分配内存，使其存放在堆上，从而保证后续访问的有效性。由此可见，局部变量的存储位置具有一定灵活性，具体策略取决于编译器实现与程序需求。函数的局部变量生命周期对应函数调用周期，即调用时创建、调用结束时销毁。若将局部变量存放于堆区，显得“小题大做”，因堆上数据生命周期通常较长，可能持续整个程序运行。故局部变量应合理存放于生命周期匹配的存储区域。具体放置位置需结合变量生命周期特征谨慎权衡，保证程序正确性及资源有效利用。

负责任且高效的编译器应尽可能将变量分配至寄存器。因现代计算机体系结构中，寄存器访问速度通常比内存快数十倍乃至上百倍。正是基于访问效率的巨大差异，现代高度优化的编译器优先将变量分配至寄存器，以提升程序执行效率。

然而，给数据分配计算资源问题并非简单。变量由程序员声明，且数量通常不受限制。举例来说，一个函数中可能声明成千上万个变量，但实际物理机器寄存器数量有限，远不可能拥有无限寄存器。假设仅有 16 个寄存器，而变量数量成千上万，如何将变量有效分配到有限寄存器中，便成为编译器设计者必须重点考虑的问题。这也是编译器研究中的重要领域，称为寄存器分配。后续课程将对此进行详细讲解。

## 指令选择与等价性保障

在代码生成的下一个阶段，一个重要的问题是为源程序级别的代码选择合适的机器指令。正如前面所述，源程序中存在一条语句`S`，而这条语句可以由若干条机器指令共同实现。已经强调，最重要的目标之一是保证等价性，即源程序中的语句 `S`所执行的功能，应当与目标机器代码中若干条指令联合完成的功能完全一致。这里的“完全一致”指的是从外部表现来看，两者的行为应保持一致，例如输入输出等方面。

典型的编译器设计者必须考虑若干关键问题。首先，需要明确源程序中的代码结构，包括表达式、语句、函数调用、类、包等各种语言构造。与此同时，还需深入理解机器指令的种类和功能，如算术运算指令、比较与跳转指令、函数调用与返回指令等。因此，要用机器指令实现高层代码的等价语义，首先必须保证等价性；其次，对编译器设计和实现者而言，要求其对机器指令集体系结构（ISA）有充分而深入的了解。对指令集的熟悉程度，往往直接决定了生成代码的质量。虽然当前已有许多研究致力于开发自动生成代码生成器的工具，类似于词法分析器自动生成器，但在现代编译器的设计与实现过程中，手工构造代码生成器仍然是主流做法。由此可见，编译器构造者必须对目标机器的指令集体系结构具备深刻理解，这也体现了编译原理作为计算机科学领域中既复杂又综合的学科特点。

到这里可以看到，除了对源语言要有非常深入的理解之外，同时还必须对底层目标体系结构有充分的认识。在接下来的几讲中，将先介绍整个讲解的路线图。刚才只是从高层次上概括了代码生成阶段可能遇到的重要问题。为了更清晰地理解其中涉及的关键问题以及编译器设计者所需采用的解决方案，将研究两种不同架构下的代码生成技术，并结合两个具体计算机体系结构的例子来分析。从同一高层语言出发，探讨如何为其生成目标代码。通过这样的学习过程，将对不同风格的机器代码生成技术有更全面深入的认识。

# 栈式计算机上的代码生成

## 栈式计算机概述

本讲将与大家一起探讨栈式计算机上的代码生成技术。这正是上一讲中提到的两种体系结构中的第一种。首先，介绍栈式计算机的基本概念及背景。栈式计算机在计算机体系结构设计历史上曾非常流行。大约在上世纪70年代，许多真实的物理栈式计算机被广泛使用。然而，随着时间推移，栈式计算机因执行效率普遍较低，逐渐退出历史舞台。如今，几乎没有厂商继续开发物理栈式计算机。

那么，为什么今天仍然首先讨论栈式计算机上的代码生成技术？主要有两个原因：
	首先，栈式计算机上的代码生成在所有可能的体系结构中最为简单直观，其本质是一个非常直接的递归算法，使代码生成过程更易理解和实现。
	其次，尽管物理栈式计算机已基本退出历史舞台，但许多虚拟机仍采用栈式计算机的架构设计。当前许多虚拟机的内部结构实际上基于栈式计算机思想实现。

举例说明：Pascal语言曾有名为Pascal P-code的虚拟机架构，基于栈式计算机设计。现今著名的Java虚拟机（JVM）最初设计时即为面向Java语言的栈式虚拟机，其生成的字节码（Java bytecode）基于栈式架构。近年来，Groovy、Scala等语言亦可运行于JVM，说明栈式虚拟机应用不限于Java语言。此外，PostScript（一种用于制图的语言）同样基于栈式虚拟机设计。类似基于栈式架构的虚拟机还有许多，感兴趣者可查阅维基百科等资料了解更多。

首先研究栈式计算机的代码生成技术，原因有二：
	第一，基于栈式计算机架构，代码生成较为简单直观，便于理解与学习；
	第二，该技术具有较强实际意义，掌握后甚至可直接生成JVM字节码，使程序运行于真实JVM虚拟机，实用且具现实价值。
## 简易栈式计算机结构

接下来，将研究一个非常简单的栈式计算机，简称“stack”。其结构较为简洁，主要由三部分组成：

第一部分：Memory（内存），用于存放程序中所有声明的变量，每个变量占用内存中一个存储单元。

第二部分：Stack（栈），作为计算操作的空间。例如执行加法时，两个操作数及结果均放于栈中操作。栈的结构如下图所示，约定栈底（bottom）在此，栈顶指针 `top` 指向当前栈顶的实际元素，而非下一个待插入位置。该约定与数据结构中常用栈实现有所不同，但在许多真实计算机中被采用。元素位于此，`top` 指向栈顶元素。

第三部分：执行引擎（算术逻辑单元 ALU），负责算术和逻辑运算。为简化起见，暂省略控制单元等其他部分。

该栈式计算机指令集共有七条指令：

```
S → push number           
   | load x         
   | store x               
   | add      
   | sub      
   | times      
   | div      
```

- **push number** ：将立即数压入栈顶，栈大小加1。
- **load X** ：将变量 X 从内存读入栈顶，栈大小加1。
- **store X** ：弹出栈顶元素，并赋值给内存变量 X。
- **add**、**sub**、**times**、**divide** ：分别对应整型加、减、乘、除四种算术运算。

需额外说明的是，这些指令实际上是Java字节码（Java bytecode）的子集。Java字节码操作码由一个字节表示，理论上可编码256条指令。现JVM定义指令数量约220余条，尚未用尽。本书仅选取其中七条以讲解基本原理。如有兴趣，读者可查阅完整JVM字节码指令集，其中包含本书所述指令。

## 指令执行语义分析

接下来重点分析每条指令的语义。这印证前述观点：作为编译器开发者，必须深入理解机器指令集，尤其指令语义，方能有效完成代码生成工作。

第一条指令 `push number` 的操作语义为：执行时，先将栈顶指针 `top` 自增1，即 `top++`，再将栈顶位置 `stack[top]` 赋值为给定立即数 `number`。换言之，栈顶向上扩展一格，将指定数字存入该位置。

```plaintext
push NUM:
   top++;
   stack[top] = NUM;
```

若执行前栈状态如图所示（`top` 指向当前栈顶元素），执行 `push 3` 后，数字3被压入栈顶，栈大小增1。

该语义非任意设定，而遵循JVM官方规范。规范以执行前后栈状态图形化展示指令效果，使语义直观明了。本书亦采用类似方式，系统介绍每条栈式计算机指令执行行为，便于理解其作用及代码生成中的意义。

---

第二条指令 `load x` 的语义为：将内存变量 `x` 值加载到栈顶。形式化执行过程为：

```
load x:
   top++;  
   stack[top] = x;
```

即栈顶指针加1，将变量 `x` 当前值读入栈顶，栈深度加1。执行前，`top` 指向当前栈顶；执行后，`x` 值为新栈顶元素。

需注意，`load x` 是典型访存指令，其本质为内存向计算栈传送数据。与 `push number` 类似，均引起栈结构变化，为后续算术运算准备操作数。

变量 `x` 具体存储于内存中，每变量占一存储单元。假设程序含变量 `x`、`y`、`z`，对应内存地址分别为：

- memory[x] → 地址 A  
- memory[y] → 地址 B  
- memory[z] → 地址 C  

执行 `load x` 即从内存地址 A 读取值压入栈顶，体现栈式计算机运行时变量值必须加载至栈的基本特性。

---

与 `load x` 指令相反，`store x` 实现栈到内存的数据传送。其语义为：将栈顶元素赋值给内存变量 `x`，即

```
store x:
   x = stack[top];  
   top--;
```

先赋值，后将栈顶指针下移一位，表示栈顶元素弹出，栈大小减1。

执行效果为：假设栈顶元素值为 `v`，执行后变量 `x` 赋值为 `v`，该元素从栈中移除，栈顶更新。

由 `load` 与 `store` 指令可见，栈式计算机中数据在内存与计算栈之间流动明确，且每条指令语义简洁，这也是栈式计算机便于代码生成的重要原因。

---

接着考察第一条算术指令：加法（`add`）。其执行分三步：

```
add:
   temp = stack[top-1] + stack[top];
   top -= 2;
   push temp;
```

1. 取栈顶两个元素 `stack[top]` 与 `stack[top-1]`，相加并存入临时变量 `temp`；
2. 栈顶指针下移两位，`top -= 2`，表示弹出两个操作数；
3. 将结果 `temp` 写入新栈顶位置。

整体效果为：将两个栈顶元素加法运算结果压回栈中，栈规模减1，栈顶元素变为加法结果 `U + V`。

减法（`sub`）、乘法（`times`）、除法（`divide`）指令执行流程与此类似，唯一差别为步骤一中运算符不同，分别为 `-`、`*`、`/`。建议仿照加法语义，完成这三条指令的详细执行语义描述。

## 伪指令与变量内存分配

接下来介绍变量内存分配所使用的伪指令。在此，需要特别说明“伪指令”这一术语的含义。在前文中提到，变量在运行时所占用的位置是在内存（memory）区域中。由于一个程序中声明了多少变量在编译阶段是静态已知的，因此在本章所使用的栈式计算机（stack machine）模型中，我们引入一种伪指令 `.int x`，用于表示为变量 `x` 分配一个内存单元，也即在内存区域中为其保留一个位置。

该模型仅支持一种基本数据类型，即 `int`，即整型数据。通常情况下，一个 `int` 类型变量占用 32 位（即 4 个字节）的内存空间。上述伪指令 `.int x` 中，前缀的点号（`.`）用于表示该指令为“伪指令”，其后接变量名 `x`。

之所以称为“伪指令”，是因为这类指令**不会**由算术逻辑单元（ALU）执行。在程序被装载或读入时，机器会预先处理所有伪指令，根据其内容为相关变量分配内存空间。由于这些变量的声明在程序的静态结构中是已知的，因此分配过程可以在程序执行前完成。换言之，程序中含有多少条此类伪指令，就会相应分配多少个内存单元用于变量存储。

与之相对的是“真正的指令”，如算术运算或栈操作，它们需要在程序运行时由 ALU 逐条解释并执行。通过接下来的示例，我们可以进一步理解程序中的指令、伪指令、变量声明以及表达式是如何被翻译并执行的。
## 示例程序及指令翻译

通过下面的示例，能够清晰地理解指令、伪指令、变量声明以及语句表达式在编译过程中分别被翻译为何种形式。

下面是一段符合C语言规则的程序代码，其中声明了三个整型变量X、Y、Z，并包含若干语句。

``` c
int x;              
int y;             
int z;              

x = 10;            
y = 5;              
z = x + y;
y = z * x;
```

经过翻译后，这段程序对应的栈式计算机指令序列大致如下。为了便于说明，在指令前加上了行号和冒号，代表指令的编号，实际机器中也可以理解为指令在内存中的地址。

```asm
.int x
.int y
.int z

1:  push 10
3:  store x

4:  push 5
5:  store y

6:  push x
7:  push y
8:  add
9:  store z

10: load z
11: load x
12: times
13: store y
```

三条变量声明被翻译成了三个伪指令：`.int x`、`.int y`、`.int z`。当机器读取该程序时，会在之前提到的三部分结构——栈（stack）、算术逻辑单元（ALU）、内存（memory）中，特别是在内存区域为这三个变量分配各自的空间，分别对应变量X、Y、Z。

来看下一段代码：`x= 10`。这条语句会被翻译成两条指令，首先是 `push 10`，然后是 `store x`。我们可以简单分析这两条指令的执行过程。

一开始，栈是空的，假设栈是向右扩展的。执行 `push 10` 指令时，数字10被压入栈顶。接下来执行 `store x` 指令，根据其语义，栈顶元素被弹出并存储到变量X对应的内存位置。因此，此时栈再次变为空，而变量X中存储的值变成了10。

通过这两条指令的执行，可以清楚地看到高层语言中赋值语句 `x = 10` 是如何通过栈操作完成的。类似地，其他语句也可以按此方式翻译和执行。例如，`push 5` 和 `store y` 等指令序列对应着高层语言中的赋值语句。这里不再详细展开，留作练习，建议自行分析这些指令与源语言语句的对应关系。

## 表达式的代码生成

先明确一个问题，即准备编写一个将 C-- 语言程序转换为栈式计算机目标代码的代码生成算法。

```c
D -> T id;D
	|
T -> int
	| bool
S -> id = E
	| printi (E)
	| printb (E)

	| id
	| true
	| false
	| E + E
	| E && E
```
而下面部分则是栈式计算机的指令集语法，正如上一讲所介绍的。
```asm

   | load x         
   | store x               
   | add      
   | sub      
   | times      
   | div      
```

为了实现从 C-- 语言到栈式计算机指令集的转换，我们需要编写一个函数 F，使其能够将给定的 C-- 程序翻译成对应的栈式计算机指令序列，完成这一转换过程。

接下来将一起讨论一种称为“递归下降”的代码生成算法。需要注意的是，这个术语并非首次提及，在语法分析部分也曾涉及过递归下降算法。之所以称其为“递归下降”，是因为该算法通过编写多个递归函数，采用递归下降的方式遍历程序的结构，从而实现代码的生成。

既然采用递归下降的方法，我们可以设想需要编写几个对应非终结符的函数，分别是 P、D、T、S 等。例如，针对非终结符 P，我们需要编写一个代码生成函数，该函数接收两个参数：D 和 S，因为 P 的产生式右侧包含变量声明（D）和语句（S）两个部分。同样地，对于非终结符 D，我们也要编写相应的代码生成函数，考虑其右侧可能包含 T、id 和 D 等部分，需要将这些作为参数传入。对于 T、S 以及 E 等非终结符，也都需要编写对应的递归函数。总共需要为这五个非终结符编写五个递归函数。回想之前的递归下降语法分析算法，会发现这种结构与代码生成的递归下降算法非常相似。

在之前，也是针对每个非终结符编写相应的函数，但当时编写的是语法分析函数。而在这里，为每个非终结符编写的是代码生成函数。当然，采用的命名约定是在函数名前加上“栈”前缀，此前也使用过“Pass”前缀。

---
**代码生成函数 Gen_E 的设计**

接下来详细说明递归下降代码生成算法中各个函数的具体实现。

首先来看表达式的代码生成算法，即函数“Gen_E”，其输入参数为一个表达式。在编写该算法时，乃至编写任何代码生成算法时，一个非常重要的概念是“不变式”（invariant）。需要注意的是，这里所说的不变式不同于“不变量”（constant），它是指在所有可能的情况下始终成立的一种约定或状态。设定的核心不变式是：**表达式在计算完成后，其结果始终位于栈顶**。下面将结合具体示例来说明，在表达式的不同构造形式下，如何保持这一不变式的成立。

在表达式代码生成过程中，我们通常会采用分情况处理的方式进行讨论，即通过 `switch(e)` 结构来区分不同类型的表达式。

```c
Gen_E(E e)
 switch (e)
  case n: emit ("push n"); break;
  case id: emit ("load id"); break;
  case true: emit("push 1"); break;
  case false: emit ("push 0"); break;
  case e1 + e2 : Gen_E (e1);
                 Gen_E (e2);
                 emit ("add");
                 break;
  case ... : ... //similar
```

**各类表达式的处理分析**

现分别对几类典型表达式给出说明：

首先，若表达式 e 是一个整型常量 n，即 `case n`，此时指令为：

`emit("push n");`

这条指令对应的是栈式计算机中将立即数压入栈的 `push` 指令。当该指令执行时，常量 `n` 将被压入栈顶，从而使表达式的值保存在栈顶位置，满足我们所设定的**不变式**：表达式的值总位于栈顶。

接下来，若表达式为变量 `id`，即 `case id`，则对应的指令为：

`emit("load id");`

例如当 `id` 为变量 `x` 时，生成的指令即为 `load x`。其作用是将变量 `x` 的当前值加载并压入栈顶。这部分内容可以类比整型常量的情况，留作练习，可自行验证其不变式的保持。

对布尔常量 `true` 和 `false` 的处理则稍有不同。虽然源语言中支持布尔值，但目标机器仅支持整型，因此需进行转换：

- 对于 `true`，生成指令：
    
    `emit("push 1");`
    
- 对于 `false`，生成指令：
    
    `emit("push 0");`

即将布尔值转换为整型数：`true` 对应 `1`，`false` 对应 `0`。这一约定类似于 C 语言中的处理方式，在 C 中 `0` 表示假，非零表示真；而在此处，我们将 `1` 明确表示为真，`0` 表示为假。经过此转换后，表达式计算中将不再出现布尔类型，所有栈中保存的值均为整型数。

再看加法表达式 `e1 + e2`，对应处理逻辑如下：

```
Gen_E(e1);
Gen_E(e2);
emit("add");
```

此处涉及递归调用，首先对子表达式 `e1` 调用 `Gen_E` 生成对应的汇编指令序列。根据不变式的定义，执行完该序列后，`e1` 的值位于栈顶。

接着处理 `e2`，调用 `Gen_E(e2)` 生成代码。由于 `e2` 的代码在 `e1` 之后执行，其计算结果将压入当前栈顶，因此 `e2` 的值在栈顶，`e1` 的值在其下方，栈布局如下：

`... e1 的值 e2 的值 (栈顶)`

此时 `add` 指令。根据其语义，`add` 从栈中弹出两个操作数（即 `e2` 与 `e1` 的值），求和后将结果压入栈顶。执行完该指令后，栈顶即为表达式 `e1 + e2` 的结果，因此不变式依然保持。

这一过程体现了不变式的核心含义：无论表达式结构如何复杂，经过一系列规范的指令生成与执行，其计算结果始终位于栈顶。

至于逻辑与表达式 `e1 and e2`，其处理方式与加法表达式类似，可留作练习。需要指出的是，目前的目标机指令集中尚未包含用于计算逻辑与的指令，因此在实际实现过程中，可能需要扩展目标指令集，新增用于逻辑与运算的指令，并据此修改代码生成过程以支持该操作。

## 语句的代码生成

在前面介绍了表达式的目标代码生成方法之后，本节将继续介绍如何使用递归下降方法为语句生成目标代码。为此，定义一个新的代码生成函数 `Gen_S`，其输入参数是一条语句 `S`。

在进行语句的代码生成时，依然遵循一个重要的不变式：**在该语句生成出的代码执行前后，栈的规模保持不变**。也就是说，如果在执行前栈的规模为 `N`，那么在执行完语句所生成的代码之后，栈的规模仍为 `N`。

```c
Gen_S(S s)
    switch (s)
        case id = e : Gen_E(e);
                      emit("store id");
                      break;
        case printi(e) : Gen_E(e);
                         emit ("printi");
                         break;
        case printb(e) : Gen_E(e);
                         emit ("printb");
                         break;
```

接下来逐一说明该不变式是如何在不同语句类型中得到保证的。

**赋值语句**

首先来看简单的赋值语句 `id = e`。为了生成该语句的代码，首先递归调用 `Gen_E` 来为表达式 `e` 生成代码。该递归调用体现了“递归下降”代码生成的基本思想，即遇到子结构时通过递归调用来处理。

执行 `Gen_E(e)` 所生成的代码后，会在栈顶压入表达式 `e` 的值。接着，再发射一个 `store id` 指令。该指令将栈顶元素弹出，并将其存入变量 `id` 对应的内存区域。

来看栈的变化过程：

- 执行 `Gen_E(e)` 生成的代码后，栈增长 1；
    
- 执行 `store id` 指令后，栈缩减 1。
    

因此，整个赋值语句执行前后，栈的规模保持不变，不变式得到保持。

从语法树角度来看，赋值语句的抽象语法树结构如下：

![7.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291104411.png)


我们在生成代码时采用**后序遍历**的方式：

1. 首先遍历左子树（变量 `id`，无需生成代码）；
    
2. 接着遍历右子树（表达式 `e`，调用 `Gen_E`）；
    
3. 最后回到根节点（赋值操作），发射 `store id` 指令。

因此，赋值语句的代码生成过程对应于其抽象语法树的后序遍历。

> 值得注意的是，代码生成的遍历顺序与语义分析的遍历顺序是相同的，因此许多编译器会将语义分析与代码生成或中间代码生成模块合并实现。但在教学实践或实验中，为了简化实现，通常会将这两个阶段分开处理。当然，也可以尝试将它们合并以提升效率。

**打印语句**

对于打印整型表达式 `printi(e)` 的语句，其代码生成过程如下：

- 首先递归调用 `Gen_E(e)` 生成表达式 `e` 的代码，结果值压入栈顶；
    
- 然后发射指令 `printi`，将栈顶的整型数弹出并打印，同时输出一个换行。

由于 `printi` 指令并未在最初的指令集定义中出现，因此需要扩展目标指令集，新增指令`printi`,该指令的语义为：**从栈中弹出一个元素，并将其打印到屏幕**。

由于：

- `Gen_E` 增加栈深度 1；
    
- `printi` 减少栈深度 1；
    

因此，整个 `printi(e)` 语句执行前后，栈的规模不变，符合不变式要求。

---

`printb(e)` 与 `printi(e)` 十分相似，都是先调用 `Gen_E(e)` 将表达式结果压入栈中，再通过 `printb` 指令将栈顶元素打印出来。

该指令的语义为：**从栈中弹出一个元素，将其解释为布尔值（1 表示 true，0 表示 false），并打印到屏幕上**。

由于流程与 `printi` 完全一致，因此不再赘述，可自行参考 `printi` 的实现理解。

## 类型的代码生成

在源语言中，变量声明由类型与标识符组成。我们为类型定义代码生成函数 `Gen_T`，其输入为类型 `T`。

```c
Gen_T(T t)
	switch (t)
		case int : emit (".int");
				   break;
		case bool : emit (".int");
					break;
```

由于目标机仅支持整型，因此：

- 若源语言中的类型为 `int`，则生成伪指令 `.int`；
    
- 若源语言中的类型为 `bool`，也生成 `.int`，因为布尔类型用整型模拟（true 对应 1，false 对应 0）。

## 变量声明的代码生成

我们再定义变量声明的代码生成函数 `Gen_D`，它处理形如 `T id; D` 的声明列表：
```c
Gen_D(T id; D)
	Gen_T (T);
	emit ("id");
	Gen_D (D);
```
1. 首先调用 `Gen_T(T)` 为类型生成代码；
    
2. 然后发射变量标识符 `id`；
    
3. 最后递归调用 `Gen_D(D)` 处理后续声明。
    
因此，该算法可以依次为所有变量生成 `.int` 声明指令。

**程序整体结构的代码生成**

程序的整体结构由变量声明部分 `D` 和语句部分 `S` 组成。程序的代码生成函数 `Gen_P` 定义如下：

```c
Gen_P (D S)
	Gen_D (D);
	Gen_S (S);
```

1. 接收两个参数：变量声明 `D` 和语句 `S`；
    
2. 先调用 `Gen_D(D)`，为所有变量生成目标代码；
    
3. 再调用 `Gen_S(S)`，为语句生成目标代码。
    

经过上述过程，即可为整个程序生成完整的目标代码。

## 运行栈式目标代码的三种方式

在完成了代码生成后，一个有趣的问题随之而来：我们如何运行所生成的这些汇编指令，从而获得程序的执行结果？实际上，有多种可行的运行方式，以下列出三种典型方案：

---
**1 在真实的物理栈式机器上运行**

最直接的想法是，寻找一台真实存在的物理栈式计算机，然后将生成的代码部署并运行在该机器上。  
然而，实际操作中这种方法往往难以实现。原因在于栈式计算机目前已较为少见，已经逐渐被主流的寄存器式计算机所取代。因此，要找到一台现实可用的栈式物理设备并不容易。不过，也可以尝试在网上查找一些古老的栈式计算机的模拟器，将其部署在本地机器上进行实验运行。

---

**2 编写虚拟机或解释器**

考虑到所使用的指令集完全是自定义的，并不依赖任何具体物理机器，因此可以编写一套专门的虚拟机或解释器来模拟这些指令的执行。该虚拟机根据我们定义的指令集规则逐条解释执行，从而完成整个程序的运行。

这种方法在现代编译系统中非常常见，典型的例子是 Java 虚拟机（JVM）。JVM 采用了一套称为 Java 字节码（Java Bytecode）的中间语言，配合 HotSpot 等虚拟机即可完成 Java 程序的执行。你也可以尝试编写一个小型的虚拟机来解释执行你自己生成的代码，这实际上就是一个简化版本的解释器。

---

**3 在非栈式机器上模拟栈式计算机**

尽管现在主流的计算机架构（如 x86）不是栈式结构，但它们通常也提供了栈相关的指令和寄存器（如 `esp`, `ebp`），可以用来模拟栈的行为。因此，我们可以在这类非栈式架构上通过模拟实现栈式机器的执行逻辑。

例如，在 x86 架构上，我们可以通过 `push` 和 `pop` 指令手动管理调用栈，模拟我们设计的栈式指令的执行过程。这种模拟方式实际上与现代虚拟机中的 **即时编译技术（JIT, Just-In-Time Compilation）** 密切相关。JIT 的核心思想是：在虚拟机运行时将高级中间代码（如 Java 字节码）动态地翻译成底层机器码（如 x86 指令），并在物理机上执行，从而提高运行效率。

因此，在非栈式机器上模拟执行栈式指令的方式，正是现代虚拟机技术的核心思想之一，也具备现实意义。

---

尽管在教学中设计的是一种“虚拟”的栈式机器，但这套指令体系不仅具有理论上的严谨性，也可以通过多种技术路径实现其在真实环境中的运行。无论是通过虚拟机、模拟器，还是即时编译，这些方法都能使我们所设计和生成的汇编指令在现实世界中“活”起来，得出真正的执行结果。因此，生成的代码不仅仅停留在“理论”层面，而是具备实际可运行性的。

# 面向寄存器计算机的代码生成

## 背景介绍

在本讲中，将继续探讨面向寄存器计算机的代码生成算法。前面已经分析了栈式计算机的体系结构及其对应的代码生成技术。接下来，将重点讨论另一种主流计算机体系结构——寄存器计算机（Register Machine）。

---

首先对寄存器计算机的背景作一简要介绍。寄存器计算机是当前最为流行的体系结构之一，主要原因在于其具有多方面的优点。首先，该结构的执行效率较高，访问寄存器的速度远快于访问内存，因此若大多数运算均可在寄存器中完成，则整体运行效率较高。其次，寄存器计算机的体系结构较为规整，这一点可通过其指令集加以体现。结构规整带来的结果是代码生成过程相对简单，不容易出现特殊情况。

所谓寄存器计算机，其本质在于基于寄存器架构进行设计。通常包括 16、32 或更多个寄存器。所有运算均需在寄存器中完成，例如执行加法操作时，两个操作数必须位于寄存器中，运算结果也必须存回某个寄存器。此外，该体系结构采用 load/store 架构，即所有内存的访问操作需通过加载（load）和存储（store）指令完成，内存本身不直接参与计算。这一特性不同于栈式计算机，其运算在栈中完成，而寄存器计算机则要求所有运算在寄存器中进行。

寄存器计算机结构规整的一个体现是其指令等长，例如典型的指令长度为 4 字节。这类结构也是 RISC（精简指令集计算机）架构的典型特征，即运算基于寄存器执行，强调指令的简洁性和执行的高效性。

---
## Reg 机器模型简述

为了便于讨论寄存器计算机上的代码生成算法，引入一个简化的寄存器计算机抽象模型，称为 Reg。该模型与栈式计算机类似，由三部分组成：内存（Memory）、寄存器组（Reg）和执行引擎（ALU）。其中，ALU 用于执行各类指令，其功能未发生变化。不同于栈式计算机的栈结构，Reg 模型使用一组寄存器 r1 到 rn 表示寄存器集合。
![9.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291104174.png)



在该模型中，寄存器用于完成计算操作，起到类似计算空间的作用。例如，执行加法时，加数和被加数分别位于两个寄存器中，结果写入另一个寄存器中。为简化模型的分析过程，假设该寄存器计算机拥有无限多个可用寄存器。这一设定与此前栈式计算机中对栈大小的设定类似，同样是假定为无限。该抽象设定将在本节后半部分进行说明，并讨论其实际如何消除。

此外，该模型中的内存部分用于存放溢出变量。所谓溢出变量（spill variable），是指由于寄存器数量有限，无法为所有变量分配寄存器空间时，需将部分变量存储到内存中。例如，当程序中声明了多个变量（如 `int x`、`int y` 等），而系统仅有有限数量的寄存器可供分配时，超出部分的变量就需要溢出到内存中。在本节中，考虑寄存器无限的设定条件下，暂不考虑溢出变量的问题，即认为所有变量均可成功分配到寄存器中，无需进行溢出处理。

## Reg 机器指令集

接下来将介绍寄存器计算机 Reg 的指令集，这是该模型中的一个重要组成部分。

指令的语法由一个上下文无关文法给出。以非终结符 `S` 表示一条指令，总共包括以下八种形式。

```plaintext
S → movn n, r           // 将立即数 n 赋值到寄存器 r
   | mov r1, r2         // 将寄存器 r1 的值赋值给寄存器 r2
   | load [x], r        // 从内存地址 [x] 加载数据到寄存器 r
   | store r, [x]       // 将寄存器 r 中的数据存储到内存地址 [x]
   | add r1, r2, r3     // r3 = r1 + r2
   | sub r1, r2, r3     // r3 = r1 - r2
   | mul r1, r2, r3     // r3 = r1 * r2
   | div r1, r2, r3     // r3 = r1 / r2
```

首先来看第一条指令 `move n, r`，其中 `move` 是指令的助记符。该指令表示将一个整型常量 `n` 赋值给寄存器 `r`。其中 `n` 是一个整数常量，`r` 是某个寄存器。该指令完成的是数据从立即数到寄存器的移动。

第二条指令为 `mov r1, r2`，与第一条相比助记符中少了一个字符。该指令的语义是将寄存器 `r1` 的值赋给寄存器 `r2`，完成的是寄存器之间的数据传送。

接下来的 `load` 与 `store` 为访存操作。`load [X], r` 表示从内存地址 `X` 处读取数据，并将其存入寄存器 `r`。其中 `X` 是内存中的某个变量，占据一个存储单元。该指令完成的是内存到寄存器的数据传输。相反，`store r, [X]` 表示将寄存器 `r` 中的值写入内存地址 `X`，实现的是寄存器到内存的数据存储。

以上四条指令都属于数据移动操作。其中包括立即数到寄存器、寄存器到寄存器、内存到寄存器、以及寄存器到内存的不同数据流方向。

接下来的四条为算术运算指令，分别是加、减、乘、除。例如，加法指令形式为 `add r1, r2, r3`，表示将 `r1` 和 `r2` 中的值相加，并将结果存入寄存器 `r3`。其他算术操作（`sub`、`mul`、`div`）与 `add` 操作在格式与语义上完全一致。

类似于栈式计算机，这里也为变量分配寄存器设计了一条**伪指令**。由于假设 Reg 机器上有无限多个寄存器，因此程序中声明的每个变量都可以分配到一个唯一的寄存器。该伪指令为 `int x`，语法上与栈式计算机一致，但语义有所不同。在寄存器模型中，每个变量 `x` 可以直接对应到一个寄存器。

需要强调的是，在代码生成阶段所使用的 Reg 机器是一个虚拟机，其假设具有无限数量的寄存器，例如 `R1`、`R2`……直到 `RN`，其中 `N` 可以无限增长。这种假设使得每个声明的变量或中间临时变量都能够被分配到一个独立的寄存器中。这些寄存器是虚拟寄存器。

然而，显然这种生成的代码无法直接在真实计算机上运行，因为实际硬件上的寄存器数量是有限的（通常为 16 个或 32 个）。因此，为了使生成的代码能够运行，必须将虚拟寄存器映射到真实的物理寄存器，多余的部分需要通过溢出到内存的方式处理。该过程称为**寄存器分配**，这是现代编译器中一项非常重要的优化技术，它可以显著提升生成代码的质量和运行效率。

## 代码生成算法设计
### 递归下降代码生成

接下来将介绍寄存器机器 Reg 的代码生成算法，目标是将 C-- 程序转换为 Reg 程序。与栈式计算机的代码生成类似，也可以为 Reg 机器设计一个递归下降的代码生成算法。

```
// C--程序
P -> D S
D -> T id;D
	|
T -> int
	|
S -> id = E
	| printi (E)
	| printb (E)
E -> n
	| id
	| true
	| false
	| E + E
	| E && E
```

```asm
// 指令的语法
s -> movn n, r
   | mov r1, r2
   | load [x], r
   | store r, [x]
   | add r1, r2, r3
   | sub r1, r2, r3
   | times r1, r2, r3
   | div r1, r2, r3
```

即设计如下函数：`Gen_P`、`Gen_D`、`Gen_T`、`Gen_S` 和 `Gen_E`。需要特别指出的是，与栈式计算机不同，Reg 机器中的表达式代码生成函数 `Gen_E` 具有返回值，其类型为寄存器类型 `R_t`。

### 表达式代码生成（`Gen_E`）

首先介绍表达式的代码生成过程。该过程中存在一个不变式：**表达式的值总是在返回的寄存器中**。即 `Gen_E` 函数返回的寄存器名称中保存了表达式的计算结果。

```c
// 不变式:表达式的值在函数返回的寄存器中
R_t Gen_E(E e)
	switch (e)
		case n : r = fresh();
		         emit ("movn n, r");
		         return r;
		case id : r = fresh();
		          emit ("mov id, r");
		          return r;
		case true : r = fresh();
		            emit ("movn 1, r");
		            return r;
		case false : r = fresh();
					 emit("movn 0, r");
					 return r;
		case e1 + e2 : r1 = Gen_E(e1);
					   r2 = Gen_E(e2);
					   r = fresh();
					   emit("add r1, r2, r3");
					   return r;
		case e1 && e2 : r1 = Gen_E(e1);
		                r2 = Gen_E(e2);
		                r = fresh();
					    emit("and r1, r2, r3");
					    return r;
```

若 `e` 是一个整型常量，则执行如下操作：    
```
	r = fresh(); 
	
	emit("movn n, r");
	
	return r;
```


其中，`fresh()` 用于生成新的寄存器编号。可以想象其实现为使用一个全局计数器 `i`，每次调用 `fresh()` 即返回 `i++` 的结果。因此，每次调用都会返回一个唯一的寄存器编号。

上述代码表示为该常量生成一条 `movn n, r` 指令，并返回该寄存器 `r`。从而，执行该指令后，表达式的值即存在于返回的寄存器中。不变式得以保持。

对于变量、`true`、`false` 等表达式的代码生成方式类似，可作为练习进行分析。

接下来重点分析运算表达式的处理方式：

若表达式 `e` 为加法 `e1 + e2`，则递归调用 `Gen_E(e1)` 和 `Gen_E(e2)` 分别生成子表达式的代码：
```c
	r1 = Gen_E(e1); // e1 的结果寄存器
	
	r2 = Gen_E(e2); // e2 的结果寄存器
	
	r = fresh();   // 为结果分配新寄存器
	
	emit("add r1, r2, r");
	
	return r;
```

以上过程与表达式树的后序遍历顺序一致：先递归生成左右子表达式的代码，获得其结果所在的寄存器 `r1` 和 `r2`，然后生成一条加法指令，将结果存入新的寄存器 `r3`，并返回该寄存器。

`and` 运算的代码生成过程与加法类似，可作为练习自行完成。

### 语句代码生成（`Gen_S`）

下面继续讨论语句的代码生成算法。该函数接受一个语句 `S`，然后对 `S` 的不同情况进行分支处理。

```c
Gen_S (S s)
	switch (s)
		case id = e : r = Gen_E(e);
					 emit ("mov r, id");
					 break;
		case printi(e) : r = Gen_E(e);
						 emit ("printi r");
						 break;
		case printb(e) : r = Gen_E(e);
						 emit ("printb r");
						 break;
```

先来看第一种情况：如果该语句是一个赋值语句，将某个值赋给标识符 `id`。

首先，对表达式 `e` 递归调用 `Gen_E(e)`，生成其右侧表达式的代码。该表达式的计算结果被放入某个寄存器 `r` 中。随后生成一条移动指令 `mov r, id`，将 `r` 中的值赋给 `id`。

需要注意的是，假设该目标机器拥有无限数量的寄存器，因此程序中声明的变量也将占用某一个寄存器。为了方便，假设变量 `id` 对应的寄存器名也为 `id`，因此上述代码的含义是将 `r` 中的值赋给寄存器 `id`。

对于 `printi(e)` 与 `printb(e)` 的代码生成，处理方式是类似的。

在实现过程中，类似栈式表达式，可能需要添加两条新指令：一条用于打印寄存器中的整数值，另一条用于打印布尔值。

## 示例代码生成

下面来看一个示例，是之前例子的一个变种：

```C
int x;
int y;
int z;

x = 1 + 2 + 3 + 4;
y = 5;
z = x + y;
y = z * x;
```

- 有三个整型变量 `x, y, z` 的声明；
    
- 对 `x, y` 分别进行了赋值；
    
- 其中 `x` 的赋值是一个复合表达式。

以下是其生成的代码指令序列分析：

```asm
.int x
.int y
.int z

1:  movn 1, r1       ; 将常数1赋值给寄存器r1
3:  movn 2, r2       ; 将常数2赋值给寄存器r2
4:  add r1, r2, r3   ; r3 = r1 + r2
5:  movn 3, r4       ; 将常数3赋值给寄存器r4
6:  add r3, r4, r5   ; r5 = r3 + r4
7:  movn 4, r6       ; 将常数4赋值给寄存器r6
8:  add r5, r6, r7   ; r7 = r5 + r6
9:  mov r7, x        ; 将 r7 中的值存入变量 x
10: movn 5, r8       ; 将常数5赋值给寄存器r8
11: mov r8, y        ; 将 r8 中的值存入变量 y

```

前三个变量声明生成三条伪代码形式的指令。重点分析 `x := 1 + 2 + 3 + 4` 的赋值。

可以将该表达式画成一棵抽象语法树，其中加法严格体现为左结合的结合顺序。算法将从语法树的根节点出发，按照后序遍历的方式进行递归生成代码。
![11.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291103675.png)

整个表达式的赋值共生成 9 条汇编代码，每一条都完成了简单、明确的任务。这体现了编译器将高级抽象分解为底层结构的一步步过程。

其余语句的代码生成可作为练习，可以自行尝试完成。

## 运行生成代码的策略

最后探讨一个重要问题：如何运行这些生成出来的代码？

由于假设是存在无限多个寄存器，因此这些代码并不能直接在实际的物理机器上运行（真实机器上的寄存器数量是有限的）。为了解决这个问题，有两种可行的方案：

**方法一：构建虚拟机或解释器**

构建一个虚拟机，支持无限多个寄存器的使用。实现方法之一是使用一个单链表来存储所有寄存器。由于链表长度可扩展，因此可以模拟无限多个寄存器。

**方法二：在物理机器上执行**

在物理机器上运行代码则需要额外的工作。核心任务是**寄存器分配**，即将虚拟寄存器 `r1, r2, ..., rn` 映射到有限的物理寄存器 `k1, k2, ..., km`。当物理寄存器不足以满足需求时，还需将部分虚拟寄存器**溢出**到内存中。

因此，需要设计一个寄存器分配算法，解决以下核心问题：

- 何时两个虚拟寄存器可以共享一个物理寄存器？
    
- 何时它们必须分配不同的物理寄存器？
    
有关寄存器分配的具体算法，将在后续课程中进一步深入讨论。
