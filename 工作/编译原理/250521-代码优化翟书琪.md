# 编译优化导论 — 基本认识与地位

## 1. 编译优化的重要性

- **编译优化（Code Optimization）是现代编译器设计的核心模块之一。**
- 大多数**实际生产环境下的编译器都包含优化模块**，这也是衡量一个编译器优劣的关键标准。
- 优化能力强的编译器，能生成更高效的机器代码，提升程序运行性能和资源利用率。
- 没有优化能力的编译器，实际应用价值非常有限。

## 2. 现实中的普遍现象

- 尽管很多程序员每天都使用带优化功能的编译器，但对“编译优化”本身往往认识不清，存在不少误区。
- 本讲准备帮助大家厘清这些基本概念，从高层理解编译优化。

## 3. 编译优化在编译器整体架构中的位置

- **回顾编译器前端工作流程：**
  - 程序源代码经过词法分析、语法分析，形成**抽象语法树（AST）**，这是程序的内存内部结构表示。
  - 接着语义分析器（semantic analyzer）对AST做语义检查，确认程序没有语法和语义错误。
  - 只有通过这些检查的程序，才进入后续阶段。
- **编译优化通常发生在语义分析和代码生成之间或代码生成阶段的前后。**
  - 因为优化操作通常基于已正确解析且语义完整的中间表示（IR）。
  - 这些中间表示结构更适合各种优化算法的应用。

# 编译优化在编译流程中的合理位置与原则

## 1. 优化不能放在语义分析之前

- **抽象语法树（AST）阶段是否适合做优化？**
  - 表面看似合理，但存在风险。
  - 直接在AST上优化可能“删掉”一些包含语义错误的代码，导致错误被隐藏。

## 2. 经典例子说明问题

```
if (1)
    then_branch();
else
    printf(2);  // 语义错误：printf第一个参数应为字符串，不是整型
```

- 这里，`else`分支调用`printf(2)`是语义错误。
- 优化器如果在语义分析前就执行，会发现`if(1)`条件总为真，直接删除`else`分支。
- 这样语义错误的代码被删除，语义检查阶段无法发现错误。
- 结果是程序员期待的报错“消失”了，程序行为被“改变”了，这明显违背语义一致原则。

## 3. 编译优化的原则

- **优化必须尊重源程序的语义，即不改变程序的合法行为。**
- 因此，优化必须发生在语义检查（类型检查、作用域检查等）完成之后。
- 只有经过验证无误的代码，才可以安全地进行优化处理。

## 4. 优化通常发生在哪些阶段？

- 语义分析结束后，生成各种**中间表示（IR）**。
- 编译器中可能存在多个不同的中间表示层：
  - 早期的高层中间表示
  - 低层、更接近机器码的中间表示
- 优化可以在这些不同层级的中间表示上进行：
  - 早期优化（针对高层IR）
  - 中间优化
  - 后期优化（针对低层IR或生成的目标代码）

## 5. 优化并非单点事件，而是贯穿多个阶段

- 不同阶段的IR特点不同，适合做不同种类的优化。
- 优化是多阶段的、多层次的，不局限于单一表示或单一时刻。

# 编译优化的阶段划分与定义

## 一、编译优化的三个主要阶段

1. **早期优化（Early Optimization）**
   - 在抽象语法树（AST）阶段直接进行的优化。
   - 优点：对结构化信息理解较多，适合做源代码层面的简单优化。
2. **中间期优化（Intermediate Optimization）**
   - 在中间代码（IR，Intermediate Representation）阶段进行。
   - 优点：中间代码更接近机器指令，结构和抽象层次适中，优化种类丰富且灵活。
   - 注意：不同编译器使用的IR不同，优化的难易和适用性依赖于IR的设计。
3. **晚期优化（Late Optimization）**
   - 在目标代码或汇编代码阶段进行。
   - 优点：更贴近硬件架构，可以进行针对具体目标机器的优化，如指令调度、寄存器分配等。

> **总结**：优化不是单点事件，而是贯穿编译器多个阶段，不同阶段适合不同类型的优化。

------

## 二、什么是代码优化（编译优化）？

### 非正式定义

> **代码优化**是指编译器对程序进行的一种**语义保持**的程序变换（或改写）。

### 关键词解释

- **语义保持**
  - 指程序的**可观察行为不被改变**。
  - 可观察行为指程序和外部环境之间的交互，如文件IO、设备IO、网络访问、输出等。
  - 举例：优化前程序输出数字5，优化后输出数字8，明显不是语义保持。
  - 不能删除或改变程序中应有的错误检测行为，否则程序员无法正确定位错误。
- **程序变换的目的**
  - 优化是**程序代码的改写**，目的是改善程序的某些性能指标，但不能改变程序的正确行为。

------

## 三、代码优化的典型目标和衡量标准

1. **代码体积减小**
   - 优化前代码大小100K，优化后减小至50K。
   - 应用场景：如嵌入式系统、操作系统引导程序等对代码体积有严格要求。
2. **程序执行速度提升**
   - 优化前执行10秒，优化后执行5秒。
   - 这是最常见且重要的优化目标。
3. **改善缓存行为（Cache Locality）**
   - 使程序更好地利用CPU缓存，提高执行效率。
4. **节能优化**
   - 特别针对移动设备，降低功耗。
   - 例如：减少CPU空转时间，利用休眠机制降低耗电。

> **注意**：这不是完整的列表，不同应用领域可能有不同的优化目标和权重。

------

## 四、优化是否有效取决于具体目标

- 优化效果的判断依赖于编译器当前要解决的实际问题和目标。
- 并非所有的变换都能称为“优化”，必须符合当前预期的改进目标。

# 关于编译优化的第二个基本观察 —— 不存在完全优化

## 1. 优化的目的与限制

我们已经知道，优化是紧密结合编译器优化目标的一种程序改写。接下来我们要谈一个非常重要的结论：

> **不存在完全的优化算法，即不存在一个能对任意程序都能达到最优的编译优化。**

换句话说，即使你设计了若干优化算法，对程序进行多轮优化，也不可能保证最终达到全局最优状态。

------

## 2. 为什么不存在完全优化？

### 2.1 直觉上的问题

我们或许会问：是否存在一个“万能优化器”，它对任意程序进行优化后，程序已经达到最小体积、最快速度或最优性能，无法再进一步优化了？

答案是**否定的**。

------

### 2.2 与停机问题的等价性

这个结论的证明超出了本课程范围，但核心思路是基于**停机问题（Halting Problem）**的不可解性质。

- **停机问题简介**
   给定一个程序 $P$，判断它是否会在有限时间内终止（停机），是计算理论中最著名的不可判定问题。
   即不存在一个算法 $Q$，能够接受任意程序 $P$ 作为输入，准确判断 $P$ 是否停机。
- **优化问题与停机问题的关系**
   假设存在一个完全优化算法 $\text{opt}$，它接受程序 $P$ 作为输入，能将程序优化至最小状态（例如，优化到一个无限循环的“最小程序”）。
   例如：假设有程序 $L$，它是一个无限循环程序（比如标签循环自旋的简单程序）。这个程序是最“简单”的无限循环程序。
- 如果 $\text{opt}$ 能判定并优化任意程序到最优，那么对于任意 $P$：
  - 如果 $P$ 是无限循环的程序，优化后的结果应是 $L$（无限循环最小程序）。
  - 如果 $P$ 不是无限循环，优化后的程序必定不同于 $L$。
- 因此，我们可以构造一个判断程序 $P$ 是否停机的算法 $Q$：
  - 运行 $\text{opt}(P)$，判断其结果是否为 $L$。
  - 如果是，说明 $P$ 不停机；否则 $P$ 会停机。

这实际上就是停机问题的判定算法，而停机问题被证明是**不可判定的**，不存在这样的算法 $Q$，所以：

> **假设存在的完全优化算法 $\text{opt}$ 是不存在的。**

------

## 3. 结论

- 由于停机问题的不可判定性，完全的、彻底的代码优化算法**不可能存在**。
- 优化器只能做到尽可能地提升代码性能或缩减代码体积，但无法保证达到最优或判断所有可能的程序行为。
- 因此，编译优化往往是一个启发式的、近似的过程，依赖各种具体的分析和优化策略。

# 编译优化的无尽过程与面临的挑战

## 1. 编译优化是一个永无止境的过程

我们刚才讨论了“完全优化不存在”的定理，这个结论非常深刻。它告诉我们：

> **编译优化其实是一个永无止境的过程。**

举个例子：

- 你有一个程序 $P$，做完第一个优化 $O_1$ 得到 $P_1$，运行速度变快了。
- 你再写一个优化算法 $O_2$，继续优化 $P_1$ 得到 $P_2$，速度又更快一些。
- 这个过程可以一直继续下去，优化算法可以不断叠加，程序性能总能得到进一步的提升。

这意味着，理论上永远都可以继续做优化，程序可以总是“变得更好”，也就是说没有尽头。

这也导致了一个幽默的结论：

> **“编译器从业者永不失业定理”** —— 因为总能不断添加新的优化算法来提升编译器的性能，工作永远做不完，老板也不会轻易解雇你。

------

## 2. 编译优化非常困难——理论与实践的双重挑战

为什么优化这么难？主要有以下几点：

### 2.1 优化不保证总是有效

- 一个优化算法 $P$，可能对90%的程序效果显著提升，但对剩下的10%程序效果却反而会降低。
- 换句话说，优化并不保证对所有程序都产生积极影响。不存在一种优化能对所有程序都“有益”。

### 2.2 优化的组合和顺序很关键

- 优化的效果依赖于执行顺序。先执行优化 $P$ 再执行优化 $Q$ 和先执行 $Q$ 再执行 $P$ 可能导致截然不同的结果。
- 甚至执行所有优化也未必比只执行部分优化效果好。
- 如何设计合理的优化组合和顺序，是实际工程中非常关键且复杂的问题。

### 2.3 很多优化问题是非确定的（Undecidable 或 NP-hard）

- 许多优化问题尚无多项式时间算法解决，属于计算复杂度较高的问题。
- 目前普遍采用启发式、近似算法求解，效果虽然不错，但不是理论上的“完美解”。

### 2.4 优化的正确性验证非常困难

- 从直觉上看，某个优化是合理的，但要用严格的数学证明其正确性非常复杂。
- 虽然近些年编译器正确性证明领域取得不少进展，但距离普适且简单的证明方法仍有较大距离。
- 实际生产编译器中，优化阶段往往是引入Bug的高发区。

------

## 3. 对编译优化应持有的正确态度

结合以上观察，我们应当有合理、现实的认识：

### 3.1 把该做对的做对，不求全责备

- 例如一个优化对函数数目小于100万的程序效果很好，但对更大规模的程序效果反而差。
- 由于实际中极少出现极端大规模的程序，这个优化依然是非常有价值的。
- 不必期待一个优化算法能“通吃”，而应接受它对大多数实际程序的良好表现。

### 3.2 不要期待完美的编译器

- 优化永远有改进空间，但“足够好”的优化已经是很优秀的产品。
- 编译器是否优秀，不是取决于拥有多少优化，而是优化对绝大多数程序的实际效果如何。
- 盲目追求更多优化，可能适得其反，甚至带来更多复杂性和Bug。

## 编译优化课程学习路线图

在完成了对**编译优化的宏观介绍**与整体认知的初步建立之后，接下来的课程内容将带领大家系统深入地学习编译器在各个阶段所进行的多种优化技术。为了帮助大家逐步构建清晰的知识体系，我们将按照编译器的三个主要阶段：**前端优化**、**中端优化**和**后端优化**进行讲解，辅以典型的算法分析与实际案例解析。

### 一、前端优化（Front-End Optimizations）

前端优化通常是**局部的**、**流不敏感的（flow-insensitive）**，主要集中在语法分析和语义分析阶段进行，优化对象为源代码级别的抽象语法树（AST）。这些优化主要着眼于简化表达、减少冗余并提高代码清晰度，常见手段包括：

- **常量折叠（Constant Folding）**
- **代数等价转换（Algebraic Simplification）**
- **无用代码删除（Dead Code Elimination, 局部）**

尽管这些优化看似简单，但它们是整个优化链条的基础，为后续更复杂的全局优化打下良好的前提条件。

### 二、中端优化（Middle-End Optimizations）

中端优化是在**中间表示（IR）**层面进行的，是编译器优化的核心部分。这一阶段的优化特点是：**全局性**、**控制流敏感（flow-sensitive）**，需要对程序的整体行为进行分析。

常见的中端优化技术包括：

- **常量传播（Constant Propagation）**
- **拷贝传播（Copy Propagation）**
- **死代码删除（Dead Code Elimination, 全局）**
- **公共子表达式消除（Common Subexpression Elimination）**

这些优化通常需要借助数据流分析等静态程序分析技术，配合图结构如控制流图（CFG）和支配树（Dominator Tree）进行有效实现。

### 三、后端优化（Back-End Optimizations）

后端优化是在目标代码生成阶段进行的，优化目标为汇编代码或机器码，直接影响程序的执行效率和资源使用。该阶段的优化更加贴近硬件架构，具有强烈的工程属性。

常见的后端优化包括：

- **寄存器分配（Register Allocation）**
- **指令调度（Instruction Scheduling）**
- **窥孔优化（Peephole Optimization）**

这部分内容将帮助大家理解如何将中间层次的高效代码最终转化为运行效率更高的目标机器代码。

### 四、核心理论与中间表示（Intermediate Representations）

在各阶段优化的学习过程中，我们还将**穿插讲解中间表示（IR）与优化策略之间的紧密关系**。现代编译器依赖多种中间表示形式以适配不同的优化需求，常见的形式包括：

- **静态单赋值形式（SSA，Static Single Assignment）**
- **连续传递风格（CPS，Continuation-Passing Style）**

这些 IR 形式不仅是许多现代优化算法实现的基础，也对理解数据依赖性、变量生命周期等关键概念具有重要意义。

## 前端优化 —— 常量折叠（Constant Folding）

### 一、引言

在上一讲中，我们从宏观角度对编译优化（也称代码优化）进行了整体性的观察与思考。从本讲开始，我们将深入探讨**具体的编译优化算法**，并通过分析它们在编译器的**前端、中端与后端**各个阶段的应用，帮助大家建立起完整的优化认知体系。

本讲的重点是**前端优化**，我们以其中一种最基础也最常见的优化策略——**常量折叠（Constant Folding）**为例，展开详细讲解。

------

### 二、前端优化的定位与输入输出

所谓**前端优化**，顾名思义是发生在编译器的前端阶段，通常在**词法分析与语法分析**之后，对生成的**抽象语法树（AST）**进行优化。其主要目标是尽早减少冗余表达和无意义计算，为中后端优化打下良好的基础。

前端优化的典型特点：

- 优化对象：抽象语法树（AST）
- 输入：原始 AST
- 输出：优化后的 AST

在实现上，前端优化可以采用两种策略：

1. **原地修改型**：直接对原始 AST 的节点进行修改；
2. **函数式风格（Functional Style）**：不修改原始 AST，而是基于原树构造一棵全新的、优化后的语法树。

第二种方式具有更好的纯函数性质与调试友好性，也是现代编译器中较常采用的方法。

------

### 三、常量折叠的基本原理

常量折叠是一种典型的**静态表达式求值优化**，它的核心思想是：

> 在编译期就对表达式中能确定值的部分进行计算，用计算结果直接替换表达式，从而降低运行期的负担。

#### 示例 1：数值运算折叠

```

A = 3 + 5;
```

编译器在分析该语句时，发现加法运算的两个操作数都是常量，因此可以在编译阶段直接求值并替换为：

```

A = 8;
```

**优化效果：**

- 减少 AST 的节点数（从加法树变为单个常量节点）；
- 缩小中间表示（IR）的规模；
- 编译生成的目标代码更简洁，运行效率更高。

#### 示例 2：布尔表达式折叠

```
if (true && false) {
    // then 分支
} else {
    // else 分支
}
```

上述表达式在编译时即可确定条件恒为 `false`，因此可以被折叠为：

```
if (false) {
    // then 分支（不可达）
} else {
    // else 分支
}
```

进一步配合**死代码删除（Dead Code Elimination）**技术，`then` 分支可以被移除。这个过程展示了常量折叠如何为其他高级优化（如不可达代码消除）**创造机会**。

------

### 四、常量折叠的适用范围

常量折叠不仅适用于整型表达式与布尔表达式，也可以拓展到：

- 浮点数运算（需注意精度与 IEEE754 标准）；
- 字符串拼接（在某些语言中）；
- 编译时可知的枚举或宏常量计算。

当然，其具体适用范围依赖于编译器所支持的源语言语义与目标平台能力。

### 五、算法设计思想（伪代码）

常量折叠算法可采用递归、遍历或模式匹配方式实现。以下为基于语法制导方法的常量折叠伪代码示意：

```
def constant_folding(expr):
    while expr is still shrinking:
        expr = simplify(expr)
    return expr
```

这里的关键在于：

- `expr is still shrinking`：表示表达式结构在逐步简化，例如 `(1 + 2) * 3` → `3 * 3` → `9`
- `simplify(expr)`：根据语法规则与数据类型，对子树进行常量计算和替换

这个过程可能需要多轮迭代，直到表达式无法继续简化为止。

- 常量折叠能有效减少语法树和中间表示的复杂度；

为什么常量折叠需要不断重复执行呢？
 举个例子，假设有一个表达式：


从理论角度看，这就是一种**不动点算法**（Fixed-point Algorithm），因为我们不断对表达式进行折叠，直到它达到一个“稳定状态”，再也没有变化。

### 常量折叠优化小结

1. **实现简单，应用灵活**
    常量折叠是一种非常容易实现的优化技术，既可以在抽象语法树（AST）上进行，也可以直接在中间表示（IR）上实现。它的核心思想是将编译期间可确定的常量表达式提前计算，从而减少运行时计算的负担。

2. **作为公共子函数穿插于其他优化中**
    常量折叠通常不会作为独立的单步优化孤立存在，而是作为一种公共的子程序被其他优化算法多次调用。
    例如：

   - 某个优化完成后，调用常量折叠简化新生成的表达式；
   - 再进行另一个优化，然后又调用常量折叠；
   - 多个优化交替执行，常量折叠穿插其间，进一步推动程序的简化。

   这种设计极大地提高了整体优化效果的累积和效率。

3. **必须严格遵守语言语义，特别注意异常与溢出**
    尽管常量折叠看似简单，但在实现时必须谨慎，确保不会破坏程序的语义，特别是要考虑边界条件，比如整数溢出和异常。

   举例说明：

   ```
   
   0xffffffff + 1
   ```

   - 如果这两个操作数是**有符号数**（如 32 位 int），0xffffffff 表示 -1，加 1 结果是 0，这样的折叠是安全的。
   - 如果是**无符号数**，0xffffffff 是 32 位无符号整型的最大值，+1 会发生溢出，结果回绕为 0。

   这里表面上结果相同，但问题在于某些语言（比如 ML）要求溢出时抛出异常，而 C 或 Java 并不要求。如果在 ML 这样的语言里直接折叠，会跳过抛异常的语义，改变程序的可观察行为，导致错误。

因此，**优化必须保证程序行为（包括异常和副作用）不发生变化**，这是所有优化的基本原则。

### 引出后续：代数化简

常量折叠强调的是对确定的常量表达式进行静态计算，而**代数化简**则利用代数恒等式对程序表达式进行简化。它们的思想类似，但代数化简更注重利用数学恒等式的性质（比如 `x * 1 = x`，`x + 0 = x`）进行表达式的优化，从而进一步减少不必要的计算。

### 代数化简优化介绍与示例

代数化简优化的核心思想是利用代数系统中的恒等式和性质，对程序表达式进行静态的简化和替换，从而减少不必要的计算，提升代码效率。

#### 常见代数化简规则示例

- **加法中的零元素：**
   例如表达式

  ```
  ini
  
  A = 0 + B
  ```

  由于 `0` 是加法的左零元，表达式可以简化为

  ```
  ini
  
  A = B
  ```

  这样就省略了一个加法操作。

- **乘法中的单位元素和强度削弱：**
   例如表达式

  ```
  ini
  
  A = 1 * B
  ```

  可以简化为

  ```
  ini
  
  A = B
  ```

  这里`1`是乘法单位元，直接去掉乘法操作。

  更有意思的例子是

  ```
  ini
  
  A = 2 * B
  ```

  优化成

  ```
  ini
  
  A = B + B
  ```

  看似没有减少运算次数，但乘法指令通常比加法指令耗时长（比如乘法5个时钟周期，加法2个时钟周期），所以替换成两个加法指令能加快执行速度。

  这类将高成本操作替换为低成本等价操作的优化称为**强度削弱**（Strength Reduction）。

  另外，还可以用位移操作替代乘以2，例如

  ```
  ini
  
  A = B << 1
  ```

  位移通常比乘法更快，也是常见的强度削弱技巧。

#### 注意的陷阱与语义保持

代数化简必须严格保持程序的语义不变，否则会引入错误。一个典型陷阱是涉及溢出的表达式，例如：

```
css

(i - j) + (i - j)
```

乍一看可以利用加法结合律写成：

```
css

i + i - j - j
```

但如果 `i` 和 `j` 是无符号整数，且取最大值（如 0xFFFFFFFF），那么 `(i - j)` 可能溢出产生不同的行为。

- 在某些语言中（如 ML），整数溢出会导致异常；
- 在其他语言（如 C、Java）中，溢出行为是定义良好的环绕。

若直接应用上述代数化简，可能导致程序异常行为被引入或移除，从而**改变程序的可观察行为**，这是绝对不允许的。

------

### 代数化简的实现思路

代数化简的算法同样是基于**语法制导的思想**，结合表达式树的结构，递归应用各种代数恒等式来逐步化简表达式。它与常量折叠的算法框架十分相似，只是规则不同。

最死代码删除优化（不可达代码删除）

死代码删除的基本思想是：在编译过程中，静态地识别并移除程序中那些永远不会执行的代码，也就是**不可达代码**。这类代码在程序的任何执行路径中都不会被执行到，因此删除它们不会改变程序的语义，却能减少程序体积、简化后续的编译流程。

#### 典型示例

考虑下面的代码片段：

```
if (false)
    S1;
else
    S2;
```

由于条件是常量 `false`，程序执行时永远不会进入 `S1` 分支。因此，优化后可以直接删除 `S1`，并将整个 `if` 语句替换为：

```
c

S2;
```

这种优化减少了代码的规模，同时简化了控制流。

#### 死代码删除的现实意义

你可能会觉得这样的代码情况很少，因为程序员一般不会故意写死条件的分支。但实际上在软件开发中，这类场景还是很常见的。例如：

- **调试代码开关**：
   开发时，为了输出调试信息，常写类似：

  ```
  if (DEBUG) {
      printf("Debug info...\n");
  }
  ```

  发布版本时，为了关闭调试输出，往往会将条件宏改成：

  ```
  if (false) {
      printf("Debug info...\n");
  }
  ```

  这样就产生了死代码，编译器应当能自动识别并删除这部分代码，避免无用指令的生成。

#### 在控制流图上的死代码删除

死代码删除不仅能在语法树层面实现，更常见且更强大的做法是在中间表示层的控制流图（CFG）上进行。通过对CFG做深度优先遍历，可以有效识别不可达的基本块，并将其删除。

这样做的好处：

- 显著减少程序规模和复杂度。
- 简化后续优化与代码生成阶段的实现。

#### 简单的死代码删除算法示例（语法制导）

假设输入是语句 `S`，如果 `S` 是 `if` 语句：

- 先对条件表达式 `e` 做判断。
- 如果 `e` 是一个常量 `false`，那么将语句 `S` 替换成 `S` 的 `else` 分支。
- 反之若是常量 `true`，则替换为 `then` 分支。
- 其它情况保持原样。

类似地，对于 `while` 循环，如果条件是常量 `false`，那么整个循环体都不可达，可以直接删除。

## 基于中间表示的代码优化

------

### 一、引言：优化工作的分层回顾

在上一讲中，我们重点讨论了**前端优化**，即基于抽象语法树（AST）层级进行的优化方法，如常量折叠等。那种优化具有**局部性强、流不敏感**等特点，主要依赖语法结构本身进行静态替换与简化。

本讲将视角推进到编译过程的**中端阶段**，也就是**基于中间表示（Intermediate Representation, IR）**的优化。这部分优化的目标是从更高的整体视角审视程序，在全程序级别进行更深入的静态分析与性能提升。

------

### 二、中间表示与优化的关系

在现代编译器设计中，**中间表示（IR）是连接前端与后端的桥梁**。我们可以将 IR 看作是编译器的“工作语言”，它把复杂的源语言翻译成一种更适合分析和优化的中性形式。

通常来说，一个编译器可能会使用**多层 IR**，如下图所示（略）：

```
源代码 → 抽象语法树（AST） → 中间表示一（IR1） → 中间表示二（IR2） → 汇编或目标代码
```

在中端优化中，我们针对 IR 进行分析与变换。常见 IR 类型包括：

- 三地址码（TAC / Three Address Code）
- 控制流图（CFG / Control Flow Graph）
- 静态单赋值形式（SSA / Static Single Assignment Form）
- 连续传递风格（CPS / Continuation Passing Style）

每种 IR 都有其适合的优化方式和使用场景。例如：

| IR 类型  | 优势                       | 常见优化类型               |
| -------- | -------------------------- | -------------------------- |
| 三地址码 | 表达清晰、适中抽象         | 拷贝传播、公共子表达式消除 |
| SSA      | 变量唯一性，方便数据流分析 | 常量传播、死代码删除       |
| CFG      | 控制结构显式               | 循环优化、不可达代码删除   |

因此，我们要做优化，**首先必须明确所使用的 IR 类型**。不同的 IR 将直接决定优化的策略和复杂度。

------

### 三、中间代码优化的典型特征

相比前端优化，中间代码优化具有以下几个显著特征：

1. **面向整个函数或程序**
   - 中端优化通常在控制流图（CFG）层次展开，考虑整个程序中变量和控制结构之间的交互关系。
2. **数据流敏感（Flow-sensitive）**
   - 考虑语句执行的先后顺序，对变量的定义和使用进行精确分析。
3. **跨基本块的全局优化**
   - 比如：变量在多个基本块之间的传播，公共表达式在多个路径中重复出现的消除等。
4. **与机器无关的通用性**
   - 在中间层处理优化可以保证后端生成器不被过早绑定至特定目标平台。

------

- **IR1（语法层三地址码）**：进行结构变换，如合并语句、删除无用表达式等；
- **IR2（SSA形式）**：支持复杂的数据流优化，如循环不变代码外提、强常量传播等；
- **IR3（低级 IR）**：靠近目标代码层次，可进行寄存器分配前的优化。

### 现代编译器中的中间表示与优化设计

在现代编译器的实现中，中间表示（Intermediate Representation, IR）形式多样且丰富，且不同的中间表示对优化的支持和难度有显著影响。

#### 常见的中间表示形式

- **控制流图（CFG, Control Flow Graph）**
   控制流图是现代编译器中最基础的中间表示之一，表示程序中各个基本块之间的控制转移关系。
- **控制依赖图（CDG, Control Dependence Graph）**
   该图形结构用于描述程序中语句间的控制依赖关系，特别是在并行程序优化和自动并行化领域非常重要。
- **静态单赋值形式（SSA, Static Single Assignment）**
   SSA 是一种广泛采用的中间表示，确保每个变量只被赋值一次，从而极大简化数据流分析。它被广泛应用于像 GCC、LLVM 等主流编译器中。
- **连续传递风格（CPS, Continuation-Passing Style）**
   这类中间语言多用于函数式语言的编译，便于处理函数调用和控制转移。

#### 中间表示与优化之间的关系

不同的中间表示形式天然地决定了编译器能够实现哪些优化，以及这些优化实现的难易程度。例如：

- 某些优化如局部常量折叠，在语法树上实现相对简单，但全局数据流优化则难以在纯语法树结构上完成。
- SSA 形式下的数据流分析更简洁高效，很多全局优化变得易于实现。

因此，在编译器设计时，选择合适的中间表示是**核心且关键的设计决策**。这会直接影响编译器后端的优化能力和复杂度。

#### 优化过程中的程序分析

无论采用哪种中间表示，优化通常都离不开**程序分析**，这是区别于纯粹语法制导优化的关键点。

- 语法树上的优化（如常量折叠）多是局部、基于语法规则的，即**语法制导**。
- 现代优化往往需要**全局、上下文相关的信息**，这要求做全程序的静态分析（例如控制流分析、数据流分析、依赖分析等），得到程序的行为特征和约束条件。

换句话说，现代优化流程一般分为两个步骤：

1. **程序分析阶段**：通过静态分析方法收集全局性质和上下文信息。
2. **优化重写阶段**：根据分析结果指导代码转换和重写。

这一分析-优化的模式是现代编译器设计的基础。

## 基于控制流图的优化技术 —— 常量传播

------

### 一、控制流图与优化的核心联系

在编译器中间阶段，优化工作的核心是**从程序中提取静态保守信息**，并据此对程序进行改写以提升性能。这些信息源于**程序的控制流图（CFG, Control Flow Graph）**，其本质是一种对程序可能执行路径的建模方式，适用于静态分析与优化任务。

#### 优化总体流程如下：

```
	原始程序（中间表示）
        ↓  程序分析（如到达定义分析）
保守的静态信息（变量的定义-使用关系）
        ↓  程序重写（如常量传播）
优化后的中间表示程序
```

该流程说明：**分析与优化是解耦但紧密协作的两个步骤**。前者收集事实，后者据此变换代码结构。

------

### 二、常量传播：基本原理

**常量传播**是一种基本且广泛使用的中端优化技术，它的目的是在编译时识别那些在运行时总是取相同值的变量，并将其替换为对应常量，从而为后续的优化（如常量折叠、死代码删除）铺路。

#### 基本思想：

给定如下控制流片段：

```
B1:
   x := 3
   ...
B2:
   a := x
```

若分析发现：从 `x := 3` 到 `a := x` 是**唯一可达路径**，则可将 `a := x` 重写为 `a := 3`。

#### 复杂性来源：

- 控制流路径可能有分支：即 `x` 可能在多个路径上赋过不同的值；
- 对变量 `x` 的定义不唯一或不确定，则不能传播；
- 因此需要依赖**到达定义分析（Reaching Definitions Analysis）**来判断变量值的确定性。

------

### 三、常量传播的算法流程

我们可以将该优化过程形式化为以下两步：

#### 步骤一：进行到达定义分析

对程序中每条语句 `s`，记录：

- 在该语句前**可达的所有定义集合**：`RD_in[s]`
- 分析方向：**前向分析**
- 生成项与杀死项的组合：`RD_out[s] = gen[s] ∪ (RD_in[s] - kill[s])`

#### 步骤二：根据分析结果进行程序改写

对于每一条语句 `s`：

```
若 s: y := f(x1, x2, ..., xn)

对每个变量 xi:
  - 若 xi 的定义在 RD_in[s] 中是唯一的，且是一个常量赋值（如 xi := c）
    → 则将 xi 替换为 c

若所有变量均可被替换，则该语句也可能进一步变为常量表达式
```

------

### 四、示例分析

考虑如下程序：

```
1. x := 1
2. y := 2
3. z := x + y
4. a := z
5. print a
```

#### 步骤一：到达定义分析结果如下：

| 语句编号 | 到达定义  |
| -------- | --------- |
| 1        | ∅         |
| 2        | {1}       |
| 3        | {1,2}     |
| 4        | {1,2,3}   |
| 5        | {1,2,3,4} |



#### 步骤二：应用常量传播

- 第 3 行：x 和 y 均有唯一定义 → 替换为 `z := 1 + 2`
- 第 4 行：z 是复合表达式 → 不能直接传播
- 第 5 行：a 由 z 得来，仍未确定常量值

优化后程序为：

```
1. x := 1
2. y := 2
3. z := 1 + 2   ← 替换
4. a := z
5. print a
```

------

### 五、进一步优化：常量折叠与多轮传播

**观察：\**第 3 行变成了常量表达式 `1 + 2`，可以进一步做\**常量折叠（Constant Folding）**：

```
3. z := 3
```

此时，第 4 行变为 `a := z`，z 的值是 3，可再次传播为：

```
4. a := 3
```

最终，`print a` 也可变为 `print 3`。

这说明：

- **一个优化会启发另一个优化**
- 常量传播与常量折叠需交替进行，直到收敛（无进一步优化）

------

### 六、小结

- 常量传播是一种**基于控制流图的静态程序分析技术**；
- 本质依赖于**唯一可达、值确定的变量定义**；
- 必须先做到达定义分析，才能安全进行替换；
- 多轮交替优化是现实编译器中常见策略（如 SSA 表达中的 GVN + Copy Propagation）；
- **优化间相互依赖、互为前提**，因此优化顺序组合是工程中的难点和重点。

拷贝传播优化与常量传播优化在原理上十分相似，其基本思想是：在给定的控制流图中，若某处使用了变量 X，能否将 X 的定义处的变量 Y 直接替换到该使用处。为实现这一点，需要首先进行到达定义分析，以确定变量 X 在该使用位置是否只有唯一的定义。如果确实唯一，且该定义形式为 `X = Y`，那么即可将使用处的 X 替换为 Y。

因此，基于上述观察，我们可以设计一个与常量传播类似的算法。事实上，这两个优化算法可以融合在一起实现，因为它们在逻辑上极为相似。

优化过程的第一步是进行程序分析，具体而言即执行到达定义分析。第二步则基于分析结果对程序进行重写。具体来说，当某个变量 Xi 在当前位置的定义是唯一的，且该定义形式为 `Xi = Z`，即可将程序中对 Xi 的使用替换为 Z，从而保持程序行为不变。

在此不再展开具体示例。从上述描述中可以看出，拷贝传播与常量传播优化之间具有高度的相似性。

接下来，我们来看“死代码删除”优化。这一优化有助于进一步理解为什么常量传播和拷贝传播是必要的，因为这两种优化可以在一定程度上暴露出更多死代码，从而为后续优化提供机会。

所谓死代码删除，是指识别并删除那些执行结果对程序整体行为无任何影响的代码。需要注意的是，死代码删除与我们之前提到的“不可达代码删除”并不相同。

例如，考虑如下的控制流情形：程序中某个位置包含一条简单的赋值语句，例如 `X = 5`，紧接着是 `return 0`。由于赋值语句赋予变量 X 的值在之后没有任何使用，这条赋值语句对程序的最终行为无任何影响，因此是冗余的。

这就引出了一个问题：是否可以删除这条语句？答案是肯定的。若一条语句的执行没有产生任何实际效果，则可以将其安全删除，这种优化策略即称为“死代码删除”。

这里需要明确一个关键差别：“不可达代码”是永远不会被执行的代码，而“死代码”虽然会被执行，但其执行结果并不会被程序使用，是对程序语义无贡献的部分。

为了实现死代码删除，需要引入“活性分析”（Liveness Analysis）。其核心思想是：如果某变量在某条赋值语句之后不再被使用（即在该点不是活跃的），那么该赋值语句就是无意义的，可以被删除。

所谓变量“活跃”的直观理解是：若变量 X 在某位置之后仍将被使用，则 X 是活跃的；反之，若之后再无使用，则 X 不再活跃。

下面给出死代码删除的一种基本算法框架。对于输入程序 P，第一步是进行活性分析，获取每条语句之后的活跃变量集合（即 live-out 集合）；第二步是根据分析结果对程序进行改写。

具体操作为：依次扫描程序 P 中的每条语句 S。若某条语句形式为 `Y = expression`，且变量 Y 不在该语句的 live-out 集合中，说明赋给 Y 的值在后续未被使用，那么该语句即可以被安全地删除。

该算法与前文所述的分析理论是一致的，其核心思想在于识别并移除程序中无实际用途的代码，从而简化程序并提升执行效率。
