
## 第2.8节 从DFA生成分析算法

在前面的讨论中，我们经历了从正则表达式（RE）到非确定有限自动机（NFA），再到确定有限自动机（DFA），以及DFA最小化的全过程。现在，我们将研究如何把最终得到的DFA转化为实际可运行的**词法分析器代码**，实现从抽象数学模型到具体工程实现的转换。

---

### 2.8.1 DFA的代码表示方法概述

前面构造的DFA，尽管形式上清晰，但仍是一种抽象的数学结构。在构建词法分析器时，需要将这种抽象结构映射为具体的代码实现。这一过程，可称为DFA的**编程实现**或**代码表示（Code Representation）**。

从概念上看，DFA可视为一个有向图：

- 图中的**节点**对应DFA的**状态**。
- 图中的**有向边**表示状态间的**转移**，每条边上标有触发转移的输入字符


![image.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505182120130.png)



在编译器或词法分析器生成工具（如 `lex、flex、JLex` 等）中，通常采用以下几种方式来表示DFA：
- **转移表（Transition Table）**：利用二维数组存储状态转移规则。
- **跳转表（Jump Table）**：通过一系列条件判断和跳转指令（如 `if-else if` 或 `switch-case` 结构）实现状态转移。
- **哈希表（Hash Table）**：当字符集较大时，可使用哈希表来存储稀疏的转移关系，以优化空间利用。
各种实现方式各有优劣，具体选择需根据应用场景、性能需求及存储资源等因素综合考量。

---

### 2.8.2 使用转移表实现词法分析器

**转移表（Transition Table）** 是一种直观且易于实现的DFA表示方法。我们以下图所示的、针对正则表达式 `a(b|c)*` 构造并最小化后的DFA为例： 
![WechatIMG2769.jpg](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/WechatIMG2769.jpg)
上图是我们熟悉的针对正则表达式`a(b|c)*`构造并最小化后的DFA。
我们可以将其编码为一个二维数组`table[state][char]`：

| 状态 \ 字符 | $a$ | $b$ | $c$ |
| ------- | --- | --- | --- |
| 0       | 1   | -   | -   |
| 1 (接受)  | -   | 1   | 1   |

其中，`-` 表示当前状态在遇到对应字符时没有有效转移，将进入**错误状态（Error State）**。这张表精确地定义了DFA的所有状态转移。
对应的词法分析算法框架（结合最长匹配原则）大致如下：
***
```c++
function next_token():
    state ← 初始状态 (0)
    stack ← 空
    repeat:
        c ← getchar()
        if state 是接受状态:
            clear(stack)
        push(stack, state)
        state ← table[state][c]
    until state == error

    while state 不是接受状态:
        state ← pop(stack)
        rollback(c) // 回退一个字符
    返回当前识别出的token
```
#### 转移表分析实例：

假设输入为字符串：`"abcabc"`

- 初始状态：`state=0`，读入字符`a`，转移到`state=1`；
    
- 继续读入字符`b`和`c`，始终停留在`state=1`；
    
- 当再次读入`a`时，出现出错状态（因为状态`1`无对应`a`的转移）；
    
- 算法回滚到最近的接受状态，即第一次读到`c`后的状态，识别出了`abc`；
    
- 下一次调用`next_token`时，再次从未识别的`a`开始继续识别，继续获得第二个`abc`。
    

通过这种方式，我们就能方便地实现对输入串的自动识别。

### 2.8.3 栈在分析算法中的作用（最长匹配原则）

在词法分析中，特别是为了实现**最长匹配原则（Longest Match Principle）**，确实可能需要某种形式的“记忆”或“回溯”机制。原2.8.2节的伪代码试图通过一个 `stack` 来实现这一点。

最长匹配原则指的是，当输入串的某一部分可以匹配多个词法规则时，词法分析器应选择能匹配输入字符数量最多的那条规则。例如，考虑某语言的关键字 `if` 和 `ifif`。当输入为 `ifif` 时，词法分析器应将其识别为一个 `ifif`，而不是两个 `if`。若输入为 `ififf`，则应识别出 `ifif`，剩余的 `f` 交给下一轮分析。

为了实现这一点：

1. 分析器会尽可能多地消耗输入字符，只要当前序列仍能导向一个（或多个）接受状态。
2. 每当到达一个接受状态，就记录下这个状态和当前已匹配的字符串（或其长度）作为一个潜在的token。
3. 如果继续读取字符导致进入错误状态（即当前序列不再是任何合法token的前缀），则分析器需要“回退”到**最近一次记录的接受状态**，并将对应的字符串作为识别出的token。输入流指针也需相应回退。
以状态图为例：

```
(Q0)-i->(Q1)-f->(Q2接受)-i->(Q3)-f->(Q4接受)
```

![image.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505191555323.png)

例如，对于上述DFA和输入串 `ifii`：

1. `i`: `Q0` → `Q1`。当前词素 `i`。
2. `f`: `Q1` → `Q2` (接受状态)。当前词素 `if`。记录候选token: (`if`, Q2)。
3. `i`: `Q2` → `Q3`。当前词素 `ifi`。
4. `i`: `Q3` 在遇到 `i` 时，假设没有有效转移（错误状态）。
5. 发生错误。回退到最近的接受状态 `Q2`。识别出的token是 `if`。输入流回退，使得下一个token的分析从第一个 `i` 之后（即第二个 `i`）开始。
***

![dfa_trace_ifii_on_desktop](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/dfa_trace_ifii_on_desktop.png)
这种机制保证了词法分析器能够正确应用**最长匹配规则**。在某些实现中，如果DFA本身设计得足够“贪心”且状态信息充分，可能不需要显式的栈来记录整个路径，而是通过记录最后一个接受状态及其位置来实现。如果需要更复杂的回溯（例如在NFA模拟或某些PEG解析器中），栈会更有用。对于DFA实现的最长匹配，关键是记住“最后一个成功匹配点”并能够回退输入。

### 2.8.4 使用跳转表实现词法分析器

另一种常用实现方式是**跳转表（Jump Table）**。这种方法将DFA的每个状态对应为程序中的一个代码标签（Label），并通过语言提供的控制跳转机制（如`goto`语句）进行状态间转移。这种方式本质上是一种手动展开的有限状态机，具有非常高的执行效率。

以下是一个简单的伪代码示例，展示了跳转表的基本实现思路：

```pseudo
function next_token():
    state ← 初始状态
    stack ← 空
    goto Q0

Q0:
    c ← getchar()
    if c == 'a':
        goto Q1
    else:
        error()

Q1: (接受状态)
    c ← getchar()
    if c == 'b' or c == 'c':
        goto Q1
    else:
        rollback(c)
        return token
```

在这个例子中，状态转移直接通过`goto`语句实现，每个状态处理的逻辑集中在一个代码块中，避免了查表和条件分支的开销。

跳转表优点在于：

- 空间效率高：避免使用庞大的二维转移表结构，节省内存开销；
    
- 局部性好：每个状态的处理逻辑相对集中，能提高CPU缓存的命中率；
    
- 执行效率高：省去了查表过程，适合对性能要求较高的场景。
    

例如，知名的词法分析器生成工具`flex`就广泛采用跳转表表示的方式。

---

### 2.8.5 转移表与跳转表的对比

两种方法各有优缺点，我们简单做一个对比：

| 方法  | 空间效率     | 缓存性能   | 代码清晰度  | 适用场景       |
| --- | -------- | ------ | ------ | ---------- |
| 转移表 | 一般占用较大空间 | 缓存性能一般 | 逻辑简单易读 | 状态与字符集较小场景 |
| 跳转表 | 空间占用小    | 缓存性能优秀 | 逻辑稍复杂  | 状态与字符集较大场景 |

从实践角度来看：

- 当字符集较小（如ASCII）且状态数量有限时，使用转移表的实现方式更加直观、易于调试与维护；
    
- 当处理复杂的词法规则（如支持Unicode字符集或多个子语言）时，跳转表因其紧凑的空间布局和快速的状态切换更为高效。
    

并没有一种方法在所有情景中绝对占优，具体实现需要根据应用场景和性能需求来选择。
