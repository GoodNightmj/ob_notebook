

**编译原理_中科大(华保健)_P76_7.1.1 语义分析的任务1**

您好，欢迎回来。在本部分课程内容中，我们将一同探讨编译器的另一个重要阶段 —— 语义分析。在这一讲里，我们首先来了解语义分析的总体任务，形成一个宏观的认识。

我们回顾一下，当前正在讨论编译器的前端，它包含三个主要模块。此前，我们已经探讨了词法分析器和语法分析器这两个关键部分，并且在上一讲着重讨论了抽象语法树这一核心数据结构。

在此，我们需要强调两点。其一，要再次回顾编译器所遵循的流水线结构形式。源代码经过分析后，形成了第一个重要的中间数据结构 —— 记号流。记号流再经过语法分析处理，形成了第二个重要的数据结构 —— 抽象语法树，它以内存形式呈现。总体而言，整个编译器的前端由三个核心模块和两个核心数据结构构成。希望您能从模块结构层面，建立起全局的宏观认识。

![编译器前端流水线示意图.png](https://raw.githubusercontent.com/GoodNightmj/PicGo/master/202505291139049.png)

其二，我们曾强调编译器遵循流水线模式，这带来的一个重要结果是，每个阶段都具有独立性。以词法分析为例，它仅依赖输入的源程序，并产生输出的记号流；语法分析器则仅以记号流为输入，生成抽象语法树。

而我们本讲要讨论的语义分析器模块，其输入仅为上一阶段生成的抽象语法树。这体现了阶段无关性，即我们在进行语义分析时，无需关注记号或原程序的具体情况，只需聚焦于已生成的抽象语法树。这种阶段无关性极大地简化了编译器中的许多任务，我们只需明确每个模块的输入输出，对单个模块进行研究即可。

对于语义分析器而言，其输入是抽象语法树，输出是另一种中间表示。这种中间表示与抽象语法树和记号一样，是重要的数据结构。在未进行优化的简单编译器，或编译器发展早期，语义分析器通常会直接生成目标代码，即可运行的二进制代码。但现代编译器通常需要对代码进行优化或其他复杂分析，因此往往会先生成中间表示，再由后续阶段进一步处理，直至生成目标代码。

那么，语义分析阶段的主要任务是什么呢？在不同的教材和文献中，语义分析可能有不同的名称，如类型检查或上下文相关分析。在本课程中，我们将其称为语义分析。实际上，之所以如此命名，是因为该分析阶段的工作内容比单纯的类型检查更为丰富，它包含了类型检查的部分工作，但又不止于此。

语义分析阶段负责检查程序。由于阶段无关性，其输入为抽象语法树，该阶段主要检查抽象语法树中与上下文相关的属性。需注意，抽象语法树由上下文无关文法定义，而上下文无关文法所定义的属性和信息，在语法结构上是上下文无关的。

语义分析阶段检查的是程序的上下文相关属性，具体内容因语言而异，不存在通用的情况。但典型的情况包括以下几点：

变量在使用前需先声明。这是现代编程的基本要求，即程序中使用的变量，在使用前必须进行声明，明确其类型和访问属性等，以确保后续代码对该变量的使用合法合理。
每个表达式都应有合适的类型。不同语言对合适类型的定义和构成规则可能不同，但总体而言，每个表达式都应具有明确的类型，如整型、布尔型、浮点型等，以便编译器知晓该表达式计算结果的类型。
函数的调用和定义需一致。不同语言对 “一致” 的定义有所差异。以 C 语言为例，通常要求函数调用点和定义点的参数个数相同，且每个参数的类型一致。若存在指针或类型转换情况，则需要进一步细化规则。

实际上，具体的情况远不止这些，由于不同语言的特性差异较大，这是一个无法穷尽的列表。但可以看出，语义分析所检查的属性与语法规则检查的属性相互独立，是另一套不同的规则体系。

再看代码中的加法操作，C 语言的加法运算符未在字符串类型上进行重载，它仅适用于整型和浮点型。因此，两个字符串类型相加会导致编译器报错。但需要注意的是，不同语言的语义规则可能不同，例如在 Java 中，加法运算符可用于字符串类型，此时hello + word是合法的语句。

目前，我们已经发现了至少三个错误，且这些错误均非语法错误。例如，p(23)在语法上符合函数调用的规则，但从语义角度看，未找到p的类型定义。

继续分析，主函数main中有语句f + 5。首先，编译器会检查函数f的类型，发现它需要一个整型指针作为参数，但此处的函数调用未提供任何参数，因此函数调用和定义不匹配，编译器会报错。此外，函数f的返回值类型为void，将其返回值与整型数相加是不合法的，编译器也会给出相应的错误提示。

代码中的break语句也存在问题。在 C 语言中，break语句用于跳出循环，但此处的break语句位于顶层，未处于任何循环结构内，这是一个语法错误，编译器会提示break应在do、while或for循环中使用。

最后，return语句直接返回，未携带任何值，但主函数main要求返回整型数，因此编译器会报错，提示返回值与函数要求的返回值类型不一致。这再次体现了上下文相关分析的特点，即需要结合程序的上下文信息，判断语句的合法性，而不能仅依据局部信息进行判断。

通过这个简单的示例可以看出，一个编写不当的小程序可能存在多种语义错误。语义分析阶段的主要工作就是针对类似的代码，找出其中所有的语义错误，并向程序员提供清晰合理的出错诊断信息，以便程序员根据这些信息修改代码，重新执行编译过程。

从概念上看，语义分析器的结构可以通过一个图来表示。其输入是经过语法分析后得到的抽象语法树，该抽象语法树已通过语法检查，但可能仍存在语义错误。语义分析器需要判断该抽象语法树所代表的程序是否符合程序语言规定的语义，并给出 “是” 或 “否” 的答案。与语法分析类似，语义分析器还需要明确程序语言的语义规则，即哪些是合法的，哪些是非法的。

语义分析器不仅要完成判断工作，若程序语义合法，还应生成中间代码或目标代码。在这个阶段之后，程序不应再包含任何语义或语法错误。若后续阶段出现问题，通常是编译器代码本身存在问题，而非正在编译的程序存在问题，这是一个明确的界限。

接下来，我们关注的一个重要问题是如何定义程序语言的语义。在语法研究中，我们有成熟的工具 —— 上下文无关文法，语法分析就是针对该文法的各种算法。

对于程序语言的语义，这是计算机科学中的一个重要研究领域，目前已经发展出了多种语义系统。但由于这些语义系统理论性较强，超出了本课程的范围，若您有兴趣，可以查阅相关文献。

在本课程中，传统上大多数程序设计语言采用自然语言来描述程序语言的语义。当我们最初学习 C 语言、Java 语言或其他编程语言时，通常会参考相关的编程书籍，书中会对语言的语义进行描述。例如，对于加法运算，会规定左右操作数必须为整型数才是合法的。从语法角度看，任何表达式都可以作为加法的操作数，但语义规则为加法运算添加了额外的限制。

实际上，我们学习编程语言时，语法部分相对简单，主要包括表达式的形式、控制流的结构和函数的写法等。而更多的学习内容是语言的语义，即了解在何种情况下表达式和函数调用是合法的。

目前，大多数程序语言仍然采用自然语言描述语义，这也是我们学习语言时常用的方式。但对于编译器的实现者来说，对语义规定的理解要求更高。普通的语言学习者只需知道一些常见的合法情况即可，但编译器实现者必须全面、清晰、准确地理解语言中的所有语义规定。例如，对于加法运算，编译器实现者不仅要知道两个整型数相加是合法的，还要了解一个浮点数和一个整型数相加，以及两个浮点数相加等情况是否合法。只有对语义规则有全面的理解，编译器才能进行正确的语义检测和分析。

因此，有人认为，要真正全面深刻地理解一个程序语言，最终的步骤可能是为该语言编写一个编译器。接下来的挑战是如何正确高效地实现语义分析器。在后续几讲中，我们将讨论其中涉及的主要挑战问题以及编译器中的重要解决方案，通过这些内容，您将对程序语言的语义和语义检查的实现方式有更深入的理解。

回顾语义分析在整个编译器前端中的位置，其输入为抽象语法树，输出通常为中间表示。在简单的编译器中，也可以直接输出目标代码，跳过中间表示阶段。

**编译原理_中科大(华保健)_P80_7.2.2 语义规则及实现2**
在C--语言中，只有一个非终结符E，代表表达式。该非终结符有 5 种可能的右部：整型常量N、布尔常量True和False、整型加法运算以及布尔类型的and运算（对两个布尔类型子表达式进行逻辑与操作）。通过这 5 种右部，我们可以编写一些简单但有趣的程序。

接下来，我们讨论在C--语言中，什么是类型合法的程序，什么是类型非法的程序。例如，3 + 4是一个类型合法的程序，因为加法运算适用于两个整型数，且该表达式的左右操作数均为整型数。同样，false && true也是类型合法的程序，因为左右操作数均为布尔类型的值。

而3 + true和false + true则是类型非法的程序。在C--语言中，加法运算仅适用于两个整型数，因此3 + true中一个操作数为整型，另一个为布尔型，不符合加法运算的类型要求。同理，false + true中两个操作数均为布尔类型，也不能进行加法运算。

需要注意的是，虽然C--语言的名称暗示它是 C 语言的子集，但实际上它包含了 C 语言中没有的布尔类型常量false和true。

对于C--语言，语义分析的任务是为给定的表达式e编写一个类型检查函数check(e)。该函数接受表达式e作为参数，并返回表达式e的类型。若表达式的类型不合法，则函数应报错。例如，若传入的表达式为3 + 4，函数应返回int；若传入的表达式为false && true，函数应返回bool；若传入的表达式为3 + true，函数应报错。因此，为C--语言编写类型检查器或语义分析器，等价于编写这样一个类型检查函数。对于更复杂的语言，类型检查函数可能会更加复杂或数量更多。

下面来看这个函数体的算法实现。采用switch (e->kind)语句，实际上该算法很简单，就是对e的不同情况进行分情况讨论。因为e作为一个表达式，共有 5 种不同的情况。
整型表达式
若e是一个整型表达式，也就是一个整型常量，那么其类型必然是INT，此时直接返回INT，这与我们期望的返回值类型相匹配。同理，对于false和true这两个常量，返回其类型BOOL。比较复杂的情况是复合表达式。
加法表达式
以exp_add（加法表达式）为例，该表达式包含两个子表达式，分别为e->left和e->right。我们分别对这两个子表达式递归调用check_exp函数，将左右子表达式对应的类型分别记为t1和t2。

在完成对子表达式的调用后，进行类型检查。若t1不等于INT或者t2不等于INT，则给出 “type mismatch”（类型不匹配）的错误信息。当然，一个完善的编译器应更细致地处理错误信息，例如分别明确t1不等于INT和t2不等于INT时具体的错误情况。若未出现错误，即t1和t2均为INT，则整个表达式返回INT类型的值。EXP_and（布尔类型的与运算）的处理逻辑与此非常类似，留作练习，读者可自行补充完整。
示例分析
下面通过一个示例从另一个角度加深对该算法的理解。假设传入的参数e为表达式3 + 4，显然这是一个类型合法的表达式。当e作为参数传入check_exp函数时，首先通过switch语句进行分类讨论，由于最顶层是加法节点，因此会递归调用check_exp处理左子表达式和右子表达式，处理完成后再回到根节点进行检查。

可以发现，这是一种树的后序遍历方式，即先遍历左子树，再遍历右子树，最后处理根节点。具体来说，先递归调用check_exp(e->left)，此时会进入exp_int的情况，直接返回INT类型。当该递归调用返回时，t1被赋值为INT。同理，对右子表达式进行相同的处理，t2也被赋值为INT。两个递归调用完成后，在根节点进行if判断，由于t1和t2均为INT，因此返回INT类型。

另外，对于更复杂的表达式3 + (4 + true)，它是一个类型不合法的表达式，读者可自行模拟该算法在该表达式上的执行过程，分析在何处会产生语法错误以及错误类型。


**编译原理_中科大(华保健)_P82_7.2.4 语义规则及实现4**

之前我们探讨了针对 C-- 语言简单表达式的类型检查算法，接下来将对该语言进行扩展，使其更贴近实际应用，具体是增加变量声明的处理。此时，上下文无关文法相对复杂一些。一个程序P包含两部分，即声明部分D和表达式部分E。
变量声明
重点来看变量声明的构成。变量声明的产生式为D -> T id; D，这是一个自循环结构，最终会生成一系列T id;的序列。其中，id是标识符，即变量名；T是类型，仅有int和bool两种类型符号，可用于声明变量。
表达式扩展
表达式在原有的 5 种情况基础上，新增了一种情况，即表达式可以是一个变量。下面通过几个程序示例来进一步说明。

合法程序示例：int x; x + 4，这是一个合法的程序。因为x + 4要求两边均为整型，而x通过前面的声明被指定为整型，满足类型要求。这体现了上下文相关文法的概念，即变量x的类型需要通过向上引用其声明来确定。
不合法程序示例
x + 3：该表达式中变量x在使用前未进行声明，因此程序不合法。
int x; x + false：x被声明为整型，而false是布尔类型，整型与布尔类型相加不合法。

由此可见，增加变量声明后，类型合法性的判断规则变得更加复杂和有趣，需要考虑变量声明的情况。
类型检查算法
为了进行类型检查，我们引入了一个重要的数据结构 —— 符号表。在当前对变量声明的类型检查算法中，我们将符号表理解为一个键值对的数据结构，类似于字典，它将变量名（字符串类型）映射到其对应的类型（INT或BOOL）。符号表是全局的，用于存储变量的类型信息。

此时，我们需要编写三个类型检查函数，分别用于检查程序、变量声明和表达式，因为在整个文法中有三个重要的非终结符需要处理。
check_prog函数
该函数接受两个输入，即变量声明的语法树d和表达式e。其实现逻辑如下：首先调用check_declare(d)对声明部分进行递归检查，并将返回的符号表赋值给全局符号表table；然后调用check_exp(e)对表达式进行类型检查，并返回其类型，即整个程序的类型。
check_declare函数
该函数用于处理变量声明。变量声明可能是一系列的声明语句，通过foreach (T id ∈ d)遍历每个声明，使用table_enter函数将变量名id及其类型T插入到符号表table中。
示例执行过程
以程序int x; bool y; 4 + x为例，将其转换为语法树后，根节点可拆分为变量声明部分d和表达式部分e。首先检查左子树（变量声明部分），遍历每个变量声明并将变量名及其类型插入到符号表中，最终生成全局符号表table，其中x的类型为INT，y的类型为BOOL。然后，使用生成的符号表对右子树（表达式部分）进行类型检查。

当表达式为变量时，例如x，首先使用table_lookup(table, id)在符号表中查找变量id。若未找到，则输出 “id not found”，表示变量在使用前未声明；若找到，则返回该变量的类型。

可以看出，该类型检查算法同样采用了后序遍历的方式。先遍历左子树（声明部分）构建全局符号表，再利用该符号表对右子树（表达式部分）进行类型检查。符号表在有变量声明的程序类型检查中起着关键作用，它是上下文相关检查的核心，用于存储和查询上下文相关的信息。
语句处理
最后，我们对 C-- 语言进行进一步扩展，引入语句的处理。扩展后的程序P由变量声明和语句两部分组成，变量声明部分与之前相同，而语句有三种不同的形式：

id = E：这是一个赋值语句，将表达式E的值赋给变量id。
printi (E)：这是一个预定义的标准库函数，用于打印表达式E的值，要求表达式E为整型。
printb (E)：同样用于打印表达式E的值，但要求表达式E为布尔类型，打印结果为true或false。

在本讲中，我们将一同探讨上一讲提及的、在类型检查和语义分析里极为核心的数据结构 —— 符号表。由于类型检查和语义分析属于上下文相关分析，符号表在其中起着关键作用，接下来我们将详细探讨符号表如何支持对语言中不同机制进行类型检查。

首先，我们来了解符号表的概念。符号表用于存储程序中变量的所有相关信息，是一种核心数据结构。这些信息包括类型（每个变量都会声明一个类型）、作用域（变量声明所在的层次，如程序最外层、局部或更内层的代码块等）以及访问控制信息（如 private、protected 或 public 等，不同语言包含的内容有所不同，还可能有附加在变量上的其他信息）。符号表需存储变量的所有信息，以便在检查和程序后续阶段使用。

符号表有两个重要特性。其一，其表结构要足够丰富，能涵盖所编译语言中变量可能涉及的全部信息；其二，符号表必须高效。因为编译器处理的程序可能规模庞大，变量数量众多，例如几百万行的程序可能声明几百万甚至上千个变量。所以，符号表需要合理组织，以确保编译器能高效使用，从而使编译大型程序成为可能。

我们可以编写一个符号表的接口，这与实现语言相关。若使用 C 语言实现（这是本课程默认的实现语言），可以创建一个名为 table.h 的头文件。在该文件中定义符号表的数据结构，如 typedef... Table_t; 核心问题在于如何定义符号表的数据结构，需满足两个条件：一是表达能力足够丰富，能存储变量的所有信息；二是足够高效，能处理大规模的程序和变量声明。

符号表作为典型的抽象数据类型（ADT），包含数据结构的定义和数据结构上的操作（即 API）。其 API 至少包括：

新建符号表：Table_new 用于创建一张空的符号表。
符号表插入操作：如 table_enter 或 table_insert，需要提供一个关键字和其对应的值，以实现从关键字到值的映射插入。
符号表查找操作：lookup 函数接受一个符号表和一个关键字，返回对应的值。若查找失败，通常返回一个代表空的值，如 NULL。

然而，仅给出接口是不够的，还需要进行相应的实现，这与具体的实现语言和选择的数据结构有关。

接下来，我们将介绍一种典型的符号表数据结构，但需强调的是，实际开发编译器时，不一定要采用这种结构，这里仅作概念展示。

符号表是典型的字典结构，核心在于定义 key 和 value 的数据结构。从概念上，我们可以简单地将关键字定义为字符串类型，如 typedef char *key; 对于 value，由于一个 key 可能映射到多种值，如类型、作用域等，通常会将其组织成一个结构体，例如 typedef struct {...} Value_t; 结构体的各个字段用于维护变量的各种信息。从概念上讲，符号表就像一张表格，列代表变量，行代表映射到的信息。例如，变量 x 的类型为 int，作用域为 0（表示在程序最顶层）等。

需要注意的是，在实际工程中，使用字符串作为关键字可能不是最佳选择。因为在查找时，需要进行字符串的相等性比较，而这种比较按字符进行，效率较低。因此，实际开发中可能需要对概念上的数据结构进行优化和处理。

在实现符号表时，有两个核心问题需要考虑。首先是高效性，符号表的 API 操作（如插入、查找）应能高效实现。实践中，字典结构通常采用哈希结构实现，因为哈希查找的平均时间复杂度为 O (1)，能快速完成查找操作。然而，哈希结构会随着装载因子的变化浪费一定的空间，例如 Java 标准 API 默认的装载因子为 0.25，意味着 75% 的空间被浪费，这是用空间换取时间的做法。如果在编译器构造过程中发现空间性能不佳，可以考虑使用红黑树等平衡树来实现符号表，其查找时间复杂度为 O (log N)，虽然稍慢，但不会浪费空间。因此，在编译器工程实际构造中，需要综合权衡时间和空间开销、所编译程序的特点等因素，选择合适的数据结构。

接下来，我们讨论符号表如何处理程序设计中的作用域概念。例如，在 C 语言中，变量 x 可以在最顶层声明，也可以在 if 语句块等内层作用域中再次声明。在内层作用域中引用 x 时，赋值操作会作用于最近声明的 x。

处理作用域问题有两种常见方案：

单表方案：使用一张大的哈希表，进入一个作用域时向哈希表中插入元素，退出作用域时删除元素。因为大多数语言规定变量仅在当前作用域内有效，退出作用域后不可访问。例如，最初有符号表 σ，其中 x 映射到 int；进入新的作用域后，得到新的符号表 σ1，在 σ 的基础上增加了新的映射；再进入新的块，得到符号表 σ2，又增加了新的映射。退出作用域时，需要从符号表中删除相应元素，如 σ2 删除元素后变回 σ1。使用拉链法解决哈希冲突时，新插入的元素应插入到表头，这是为了实现正确的变量屏蔽。可以思考一下为什么要采用头插法而不是尾插法。
符号表栈方案：将多个符号表组织成栈结构，栈是后进先出的数据结构。进入一个作用域时，插入一个新的符号表作为栈顶元素；退出作用域时，删除栈顶元素（即进行出栈操作）。例如，最初有一张符号表，包含 x 和 f 的映射；进入新的代码块时，创建一个新的栈顶元素，插入当前作用域的变量映射；对赋值语句进行类型检查时，从栈顶的符号表开始查找变量，如果未找到则继续向下查找，直到栈底元素。若仍未找到，则报错 “变量未声明”。这种方案可以正确检查作用域规则，你可以思考一下其中的原理。

符号表的另一个重要作用是处理名字空间，这在编译器的语义分析阶段尤为关键。名字空间指的是在一个程序中，同一个变量名可以在不同地方使用，且这些变量的作用不同，但可以同时存在而不会混淆。

以 C 语言的单链表处理模块为例，代码中可能会多次出现名为 list 的标识符，如结构体声明 struct list、全局变量 *list、函数参数 list 以及标号 list 等。编译器需要明确区分这些同名标识符，避免混淆。

实际上，程序中至少存在以下几种名字空间：

结构体标签：用于标识结构体的名字，如 struct list 中的 list。
变量名：包括函数参数、局部变量等，如函数参数 list 和赋值语句中的变量。
结构体域：结构体内部的字段名，如 struct list 中的 index 和 next。
标号：C 语言中的标签，用于 goto 语句跳转，如标号 list。

在语义分析阶段，处理名字空间的方法是为每个名字空间使用一个符号表。例如，对于 C 语言程序，需要为变量、结构体标签、标号、结构体域等分别创建符号表（如 T1、T2、T3 等）。在变量使用时，根据变量的类别到相应的符号表中查找。之前讨论的符号表组织方式（如哈希表、栈结构）适用于每个具体的符号表。
编译原理_中科大 (华保健)_P86_7.4 语义分析中的其它问题
本讲将探讨语义分析阶段可能存在的其他问题及相应的解决方案。这些问题是不同编译器在语义分析阶段可能出现的共性问题，针对具体编译器，问题列表可能会有所不同。这里以这几个问题为例，介绍处理语义分析中类似问题的通用思路。
1. 类型相容性
类型检查问题通常可归结为判断两个类型是否相容。需要注意的是，“相容” 和 “相等” 不同，相等是相容的一种特殊情况，即两个类型相等则一定相容，但不相等也可能相容。

在实际语言中，判断类型相等或相容是一个复杂且需要谨慎处理的问题。以下是两个具体例子：

名字相等和结构相等：采用名字相等策略的语言，直接比较类型名字是否相同；而采用结构相等策略的语言，可能需要递归比较结构体的各个域。例如，有结构体类型 A 和 B，它们都包含一个整型域 i，分别声明变量 x 和 y。对于赋值语句 y = x，若采用名字相等策略，由于类型名字 A 和 B 不同，该赋值非法；若采用结构相等策略，则需要递归比较各个域，若所有域都可赋值，则该赋值合法。
面向对象语言中的继承：在面向对象语言（如 Java）中，子类对象可以赋值给父类对象，这种转换称为向上转型，通常是合法的。例如，类 B 继承自类 A，将 B 类型的对象 y 赋值给 A 类型的对象 x 是合法的。为了支持这种类型检查，需要维护类型之间的继承关系，如在 Java 中继承关系呈树状结构。
2. 错误诊断
编译器质量的重要衡量标准之一是提供准确的错误信息。高质量的编译器应尽可能给出详细的错误信息，指导程序员修改代码。此外，一些优秀的编译器还能从错误中恢复，自动修正程序，使编译或分析过程能够继续进行，并准确给出出错位置。

在语义分析阶段，由于编译器采用流水线模式，中间表示依赖于前后阶段。因此，要在语义分析阶段准确报错，需要前端将位置信息完整保留并传递到当前阶段。例如，词法分析将位置信息传递给语法分析，语法分析将其标记在语法树上并传递给语义分析。若最终代码需要进行剖面或运行时性能分析，位置信息可能还需传递到代码生成阶段。这提示我们在设计语法树等中间表示时，要充分考虑位置信息的传递问题。
3. 代码翻译
在现代编译器中，语义分析模块除了进行语义分析外，还负责生成中间代码或目标代码。代码生成过程可能因编译器的复杂度而异，简单的编译器可能直接生成目标代码（如某一体系结构的汇编指令），复杂的编译器可能先生成中间代码，进行进一步分析和优化后再生成目标代码。代码生成通常是对语法树的某种遍历，常见的是后续遍历。

由于语义分析模块身兼多职，它往往是现代编译器中最庞大、最复杂的模块。其代码量通常较大，且需要进行复杂的分析，使用符号表等复杂的数据结构。因为源语言的语义处理都在这个阶段完成，而某些语言（如 C++）的语义可能非常复杂。所以，在实际工程中，语义分析阶段需要特别注意，以确保编译器完整实现源语言的语义标准。
